# Переключение моделей на ходу

| | |
|---|---|
| Дата | 2026-08-20 |
| Версия | 1 |
| Статус | на вычитке |
| Автор | Claude Opus 5 |

## Зачем

Сервис разворачивается на сервере без ускорителя, и выбор модели перестаёт быть
разовой настройкой: под разные вопросы разумны разные модели, а перезапускать
сервис ради смены — неудобно.

Требование заказчика звучало как «переключаться между моделями и менять степень
их рассуждения». Первая половина выполнима. Вторая — нет, и это выяснено
замером, а не рассуждением: см. раздел «Рассуждающие модели».

## Границы

**В работе:** выбор модели для конкретного запроса; список доступных моделей;
управление числом фрагментов в контексте; отображение того, чем получен ответ.

**Вне работы:** смена эмбеддера; автоматический выбор модели по сложности
вопроса; дообучение; управление параметрами вроде температуры.

## Что переключать нельзя

**Эмбеддер заморожен индексом.** `RAGPipeline._restore_embedder` сверяет имя
эмбеддера с манифестом и отказывается работать при расхождении — иначе запрос
и документы окажутся в разных векторных пространствах, и поиск молча начнёт
выдавать мусор. Смена эмбеддера требует переиндексации и остаётся операцией
администратора, а не переключателем в интерфейсе.

Переключаемой является **только генерирующая модель**.

## Рассуждающие модели: измеренная несовместимость

Требование «менять степень рассуждения» не реализуемо в том виде, в каком
сформулировано. Проверено на `qwen3:4b`:

| Способ | Результат |
|---|---|
| без параметров | 842 токена, 2480 символов рассуждения, ответ верный |
| `think: false` | 853 токена, рассуждение **утекает в текст ответа** |
| `think: true` | 711 токенов, рассуждение отделено, ответ верный |

`think: false` не выключает рассуждение — он перестаёт его отделять. Время
не меняется, а вместо ответа пользователь получает «Хорошо, давай разберёмся
с этим вопросом…».

Хуже в потоковом режиме. При `num_predict: 512` та же модель выдала **512 кусков
рассуждения и ноль кусков ответа**: рассуждение израсходовало весь бюджет
токенов раньше, чем начался ответ. `OllamaLLM.stream` читает только поле
`content`, поэтому наружу не ушло ничего — пользователь увидел бы «…» в течение
двенадцати секунд и пустоту.

Отсюда три требования:

1. **Ползунка «степень рассуждения» не будет.** Управление сводится к выбору
   между моделями, которые рассуждают, и которыми нет.
2. **Рассуждающие модели помечаются в списке** и не предлагаются по умолчанию.
3. **Поток обязан показывать, что модель рассуждает.** Куски из поля `thinking`
   не выводятся как ответ, но их приход означает, что процесс идёт — интерфейс
   показывает состояние вместо неподвижного «…». Без этого рассуждающая модель
   неотличима от зависшей.

Отдельно: при выборе рассуждающей модели `llm.max_tokens` должен быть заметно
больше обычного, иначе ответ не поместится после рассуждения. Значение задаётся
в описании модели, а не общей настройкой.

## Список моделей задаётся конфигурацией, а не свободным вводом

Имя модели приходит от клиента. Если передавать его в Ollama как есть,
незнакомое имя заставит её **скачивать модель** — это и непредсказуемая задержка
на десятки минут, и заполнение диска по запросу извне.

Поэтому в конфигурации появляется явный список разрешённых моделей:

```yaml
llm:
  backend: ollama
  model: qwen2.5:7b-instruct     # выбор по умолчанию
  available:
    - name: qwen2.5:7b-instruct
      title: Быстрая
      reasoning: false
    - name: qwen2.5:14b-instruct
      title: Точная
      reasoning: false
      max_tokens: 1024
    - name: qwen3:4b
      title: Рассуждающая
      reasoning: true
      max_tokens: 4096          # рассуждение съедает бюджет раньше ответа
```

Запрос с именем вне списка отклоняется с кодом 400. Пустой `available` означает,
что переключения нет и работает только `model` — так ведёт себя нынешняя
конфигурация, и обратная совместимость сохраняется.

## Область действия выбора

Модель передаётся **параметром запроса**, а не хранится на сервере.

Причина в том, что сервер сознательно оставлен без состояния везде, кроме
истории диалогов. Глобальная настройка означала бы, что выбор одного сотрудника
меняет ответы всем остальным; настройка на пользователя потребовала бы ещё
одного хранилища ради одного поля.

Интерфейс запоминает последний выбор в браузере и подставляет его в каждый
запрос. Диалог при этом может содержать ответы от разных моделей — это
нормально и даже полезно.

**Модель записывается вместе с ответом** в историю. Иначе, вернувшись к старой
переписке, нельзя понять, чем получен ответ, а при сравнении моделей это
главное, что нужно знать.

## Число фрагментов — более важный рычаг, чем модель

Замер на процессоре без ускорителя, реальный промпт из корпуса:

| | Вход | Итого |
|---|---|---|
| `top_k=5` (как сейчас) | 942 токена / 14.4 с | ~16 с |
| `top_k=3` | 631 токен / 7.1 с | ~8.5 с |
| `top_k=2` | 523 токена / 4.8 с | ~6 с |

Ответы во всех случаях верные. Время съедает чтение контекста, а не генерация:
почти тысяча токенов на входе против двадцати трёх на выходе.

Поэтому число фрагментов выносится в тот же переключатель, что и модель. На
машине без ускорителя это даёт двукратное ускорение дешевле, чем смена модели.

Границы значения: от 1 до `retrieval.candidates`. Значение по умолчанию
берётся из `retrieval.top_k`.

## Что меняется в API

| | |
|---|---|
| `GET /models` | список разрешённых моделей: имя, название, признак рассуждения, какая выбрана по умолчанию |
| `POST /ask` | принимает `model` и `top_k`; в ответе появляется, какой моделью получен |
| `POST /ask/stream` | то же; событие `done` несёт имя модели; появляется событие `thinking` |
| `GET /conversations/{id}` | у сообщений ассистента появляется имя модели |

Событие `thinking` несёт только факт, что модель рассуждает, без текста
рассуждения: показывать сотруднику внутренний монолог модели незачем, а объём
его вчетверо больше ответа.

Проверка допустимости имени модели выполняется **до** начала потока, чтобы отказ
пришёл кодом, а не событием.

## Что меняется в интерфейсе

Над полем ввода — два компактных переключателя: модель и число фрагментов.
Выбор сохраняется в браузере и не сбрасывается при перезагрузке.

Рассуждающие модели помечены в списке словом, объясняющим цену: они отвечают
дольше и подробно думают перед ответом.

Пока идут события `thinking`, вместо «…» показывается «модель рассуждает».

Под ответом рядом со временем появляется имя модели.

## Хранение

В таблицу `messages` добавляется столбец `model TEXT NOT NULL DEFAULT ''`.
Пустая строка означает «ответ получен до появления этой возможности» —
интерфейс тогда ничего не показывает.

Это ступень схемы: `SCHEMA_VERSION` поднимается до 3, лестница в `init_schema`
получает ветку `if version < 3`. Механизм уже отработан на ступени 2.

## Тесты

Существующий набор запускается без pytest, раннер по `globals()`, тестовые
функции без обязательных аргументов.

Обязательны:

- имя модели вне списка даёт 400 и в `/ask`, и в `/ask/stream`
- отказ приходит до начала потока, а не событием
- пустой `available` сохраняет нынешнее поведение: работает `model`
- выбранная модель записывается вместе с сообщением
- `top_k` вне границ даёт 422
- `GET /models` отдаёт список и отмечает выбранную по умолчанию
- ступень схемы 3 добавляет столбец на базе версии 2, не теряя данных
- сообщения, записанные до появления столбца, читаются без ошибки

Переключатели в интерфейсе автоматическими тестами не покрываются — в проекте
нет браузерного окружения. Проверка ручная: сменить модель, задать вопрос,
убедиться, что под ответом стоит выбранная; перезагрузить страницу и убедиться,
что выбор сохранился.

## Риски

**Переключение вызывает перезагрузку модели в памяти.** Ollama держит в памяти
ограниченное число моделей и выгружает лишние. На сервере с 16 ГБ смена 7b
на 14b означает выгрузку и загрузку — первый ответ после переключения будет
заметно дольше. Список разрешённых моделей стоит держать коротким и подбирать
под объём памяти сервера.

**Рассуждающая модель может не оставить места ответу.** Смягчено отдельным
`max_tokens` в описании модели, но при длинном контексте бюджет всё равно может
кончиться. Признак — пустой ответ; интерфейс обязан показать предупреждение,
а не пустой пузырь.

**Сравнение моделей внутри одного диалога сбивает контекст.** Переформулировка
уточняющего вопроса выполняется той моделью, что выбрана сейчас, а история
получена другой. Влияние невелико, но при сравнении качества это ещё одна
переменная.

**Имя модели приходит от клиента.** Список разрешённых закрывает скачивание
произвольных моделей, но список нужно поддерживать: модель, удалённая из Ollama
и оставшаяся в конфигурации, даст ошибку при первом же обращении.

## Открытые вопросы

1. **Нужен ли `GET /models` живой проверкой в Ollama.** Список можно отдавать
   из конфигурации, а можно сверять с `/api/tags` и помечать недоступные. Второе
   честнее, но добавляет сетевой вызов в каждый показ страницы.
2. **Сохранять ли выбор в диалоге, а не в браузере.** Тогда возврат к старой
   переписке восстанавливал бы и модель. Требует ещё одного столбца
   в `conversations` и решения о том, что важнее — последний выбор человека
   или последний выбор в этом диалоге.
3. **Показывать ли `top_k` рядовому сотруднику.** Для него это непонятная
   величина; возможно, вместо числа стоит дать выбор «быстро / точно»,
   скрывающий и модель, и число фрагментов за одним переключателем.
