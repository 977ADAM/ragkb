# Идентификация пользователей и история диалогов

Дата: 2026-08-19
Статус: на вычитке

## Зачем

Сервис должен вести диалог с сохранением контекста, доступный пользователю
с разных устройств. Сегодня этому мешают две вещи.

Механизм контекста в ядре уже есть и работает: `RAGPipeline.ask` принимает
историю и прогоняет вопрос через `_condense`, а `ragkb chat` этим пользуется.
Проверено замером — на вопрос «А у руководителей?» без истории сервис отвечает
про срок предупреждения об увольнении, с историей про испытательный срок.

Не хватает двух вещей:

1. Сервис не знает, кто к нему обратился. Аутентификации нет вообще.
2. Сервер не хранит состояния, поэтому переписка не переживает перезагрузку
   страницы и тем более не доступна с другого устройства.

Требование «с разных устройств» — решение заказчика, зафиксировано явно.
Оно и определило архитектуру: браузерное хранилище задачу не решает.

## Границы

**В работе:** идентификация пользователя, хранилище диалогов, привязка диалога
к пользователю, устранение двух дефектов доступа в текущем API.

**Вне работы:** чат в веб-интерфейсе (следующий шаг, отдельная спека);
разграничение доступа на уровне отдельных документов; собственный каталог
пользователей.

Работа делится на две части, которые можно выпускать независимо: сначала
идентификация, затем история. Вторая опирается на первую, обратной зависимости нет.

## Решения и их основания

### Готовые компоненты вместо собственной аутентификации

Аутентификацию не пишем. Причина организационная, не техническая: собственный
каталог пользователей становится вторым местом, где заводят и удаляют
сотрудников, и неизбежно расходится с кадровым. Уволенный сотрудник сохраняет
доступ к базе внутренних регламентов.

Keycloak разворачивается в контуре, наружу ничего не уходит, федерация с Active
Directory оставляет каталог единственным.

### Браузерный поток OIDC ведёт прокси, а не сервис

Веб-интерфейс — одна строка HTML с ванильным JavaScript внутри `api.py`.
Реализовывать в ней OAuth-клиент с редиректами, хранением и обновлением токена
непропорционально дорого.

Поэтому между браузером и сервисом стоит oauth2-proxy: он ведёт весь диалог
с Keycloak и передаёт наверх готовые заголовки. Сервис не видит ни паролей,
ни токенов, ни криптографии.

Провайдер — `keycloak-oidc`. Провайдер с именем `keycloak` помечен
в oauth2-proxy как устаревший.

Заголовок читаем `X-Auth-Request-Preferred-Username` (включается опцией
`set_xauthrequest`). Привычный `X-Forwarded-User` с Keycloak известен пустыми
значениями — на него не опираемся.

### Подделка заголовка исключается недоступностью сервиса

Схема «прокси передаёт логин заголовком» уязвима, если до сервиса можно
дотянуться в обход прокси. Снимается не инструкцией «настройте аккуратно»,
а тем, что обходить физически нечего. Способ зависит от развёртывания.

**В контейнерах.** Сервис продолжает слушать `0.0.0.0` — внутри своего сетевого
пространства имён это необходимо, иначе до него не дотянется oauth2-proxy
из соседнего контейнера. Закрывается иначе: **у сервиса `ragkb` убирается секция
`ports`**, наружу публикуется только прокси. С хоста и из сети сервис недоступен,
из сети compose — доступен единственному соседу.

**Без контейнеров.** Сервис слушает `127.0.0.1`, прокси на том же хосте.
Сокета снаружи нет.

Правки затрагивают проброс портов `docker-compose.yml:30-31` (убирается),
а для развёртывания без контейнеров — `--host 0.0.0.0` в `docker-compose.yml:47`
и `Dockerfile:37`.

### Отказ по умолчанию

`auth.mode` принимает `proxy` или `disabled`, по умолчанию `proxy`. Забытая
настройка приводит к отказу в обслуживании, а не к открытому наружу сервису.

Режим `disabled` включается явной переменной окружения, возвращает
`User(name="anonymous")` и пишет заметное предупреждение в лог при старте.

## Часть 1. Идентификация

Новый модуль `ragkb/auth.py`.

```python
@dataclass(frozen=True)
class User:
    name: str
    email: str = ""
    groups: tuple[str, ...] = ()

    def in_group(self, group: str) -> bool: ...


def current_user(request: Request) -> User:
    """Зависимость FastAPI. 401, если пользователь не установлен."""
```

Остальной код знает только про `User`. Способ его получения инкапсулирован:
смена oauth2-proxy на другой механизм правит один файл.

### Устранение дефектов текущего API

Обнаружены при разметке зависимостей, чинятся здесь же.

**`/reindex` доступен без ограничений** (`api.py:72`). Любой, кто дотянется
до порта, запускает полную переиндексацию корпуса — отказ в обслуживании.
Эндпоинт требует членства в административной группе, имя группы задаётся
настройкой `auth.admin_group`. Различать эндпоинты по ролям на прокси неудобно,
в сервисе по `User.groups` — тривиально.

**`/health` раскрывает внутренности индекса** (`api.py:40`) — число документов,
имя эмбеддера, путь к каталогу. Закрыть эндпоинт нельзя: `HEALTHCHECK`
в `Dockerfile:34` ходит туда без заголовков. Решение: без аутентификации
отвечает `{"status": "ok"}`, подробности только аутентифицированному.

### Доступ к сервису по группе

`keycloak-oidc` умеет ограничивать доступ опциями `--allowed-role`
и `--allowed-group`. Это закрывает половину пункта «Прав доступа нет»
из ограничений README: базой пользуются только члены нужной группы AD,
без единой строки кода.

Разграничение остаётся грубым — «пускать или нет в сервис целиком».
Видимость отдельных документов разным пользователям в эту работу не входит.

## Часть 2. История диалогов

Новый модуль `ragkb/history.py`. Хранилище — SQLite: стандартная библиотека,
новых зависимостей ноль, один файл для резервного копирования, запас
по нагрузке многократный. База Keycloak не переиспользуется — это связало бы
наши данные с чужой схемой.

### Схема

```sql
CREATE TABLE conversations (
    id         TEXT PRIMARY KEY,          -- uuid4
    user       TEXT NOT NULL,
    title      TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL,             -- ISO8601 UTC
    updated_at TEXT NOT NULL
);
CREATE INDEX idx_conv_user ON conversations(user, updated_at DESC);

CREATE TABLE messages (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    conversation_id TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    role            TEXT NOT NULL CHECK (role IN ('user', 'assistant')),
    text            TEXT NOT NULL,
    sources_json    TEXT NOT NULL DEFAULT '[]',
    created_at      TEXT NOT NULL
);
CREATE INDEX idx_msg_conv ON messages(conversation_id, id);
```

Версия схемы — встроенный `PRAGMA user_version`. Отдельная таблица миграций
не нужна: хватает номера и лестницы прямых обновлений в коде.

### Историю загружает сервер

Перелом относительно текущей схемы, где браузер присылает `history` в теле
запроса. Иначе работа с разных устройств невозможна: телефон не знает, о чём
спрашивали с рабочего компьютера.

Поле `history` в `AskRequest` сохраняется для CLI и программных клиентов.
Веб-интерфейс переходит на `conversation_id`.

Глубина истории, передаваемой в `_condense`, — настройка `history.window`,
по умолчанию 3 хода, как сейчас захардкожено в `pipeline.py:330`.

### Источники храним ссылками, не текстом

В `sources_json` — цитата, путь к файлу, оценка. Без текста фрагментов.

Копия чанков внутри истории означала бы второй экземпляр корпуса. Хуже:
устаревший регламент удаляют из базы знаний, а его текст продолжает жить
в переписке полугодовой давности.

Полностью это не решается — текст ответа содержит пересказ регламента.
Но масштаб сокращается существенно.

### Заголовок диалога

Обрезанный первый вопрос, до 60 символов. Без обращения к модели: генерация
заголовка добавила бы 3–5 секунд к первому сообщению.

### Срок хранения и уборка

`history.retention_days`, по умолчанию 90.

Планировщика нет. В начале запроса проверяется отметка последней уборки:
прошли сутки — удаляем просроченное, обновляем отметку. При расчётной нагрузке
90 запросов в день срабатывает регулярно, а кода на порядок меньше, чем
у фоновой задачи с её жизненным циклом и обработкой падений.

Это прямое следствие того, что сервис начинает хранить персональные данные:
журнал вопросов сотрудника — сведения о нём. Срок хранения и круг лиц
с доступом — решение организационное, техническая часть здесь.

### Технические обязательства

**`PRAGMA foreign_keys = ON` на каждом соединении.** В SQLite внешние ключи
выключены по умолчанию; без этого каскад молча не сработает и сообщения
останутся сиротами. Покрывается отдельным тестом.

**`PRAGMA journal_mode = WAL`.** При обычном режиме запись блокирует чтение.

**Соединение на запрос** через контекстный менеджер: FastAPI выполняет
синхронные обработчики в пуле потоков, а соединение SQLite между потоками
переносить нельзя.

### API

| Метод | Назначение |
|---|---|
| `POST /ask` | плюс необязательный `conversation_id`; без него создаётся новый диалог |
| `GET /conversations` | список своих, свежие сверху |
| `GET /conversations/{id}` | сообщения диалога |
| `DELETE /conversations/{id}` | удалить свой |

Во всех запросах к базе — условие `WHERE user = ?`. Фильтрация владельца живёт
в SQL, а не в интерфейсе: чужой идентификатор, подставленный руками, даёт 404,
а не чужую переписку.

## Настройки

```yaml
auth:
  mode: proxy              # proxy | disabled
  header: X-Auth-Request-Preferred-Username
  groups_header: X-Auth-Request-Groups
  admin_group: ragkb-admins

history:
  enabled: true
  path: data/history.sqlite3
  retention_days: 90
  window: 3
```

Переменные окружения перекрывают файл по существующему соглашению
`RAGKB_AUTH_MODE`, `RAGKB_HISTORY_PATH` и так далее.

## Контур развёртывания

```
браузер → oauth2-proxy → ragkb (127.0.0.1:8000)
              ↓
          Keycloak → Active Directory
              ↓
          MariaDB
```

| Компонент | Роль | Память |
|---|---|---|
| Keycloak | выдаёт токены, федерация с AD | ~1 ГБ |
| MariaDB 11.8 | база Keycloak | ~256 МБ |
| oauth2-proxy | браузерный поток OIDC | ~64 МБ |
| ragkb | сервис, петлевой интерфейс | без изменений |
| Ollama | генерация | 9 ГБ |

Прибавка около 1.4 ГБ к текущему расчёту.

Версия MariaDB фиксируется явно (`mariadb:11.8`), не `latest`: тег `latest`
однажды уедет на ветку, которой нет в списке поддерживаемых Keycloak.

## Тесты

Существующий набор `tests/test_pipeline.py` запускается без pytest и без
зависимостей. Новые тесты — в том же стиле, на `:memory:` и временных каталогах,
без сети и моделей.

Обязательны:

- чужой диалог не читается и не удаляется
- каскадное удаление сообщений действительно срабатывает
- уборка сносит просроченное и не трогает свежее
- `auth.mode: proxy` без заголовка даёт 401
- `/reindex` без административной группы даёт 403
- `/health` без аутентификации не раскрывает состав индекса

## Риски

**Ошибка в сетевой настройке.** Если ragkb окажется доступен в обход прокси,
подделка заголовка даёт вход под любым именем. Смягчено тем, что сервис не
публикуется наружу, но требует проверки при развёртывании: убедиться, что порт
8000 не отвечает ни с хоста, ни из сети.

**MariaDB — менее хоженая дорожка у Keycloak.** Официально поддерживается
(11.8, 11.4, 10.11, 10.6 LTS), уведомления об устаревании нет. Но нагрузочные
тесты и оператор Keycloak ориентированы на PostgreSQL, поэтому вероятность
встретить редкий дефект выше. При 50 пользователях риск умозрительный.

**Чат вдвое медленнее одиночного вопроса.** При наличии истории `_condense`
делает дополнительный вызов модели: +3–5 секунд к нынешним пяти на 14b.
Это свойство механизма, а не дефект.

**Хранение персональных данных.** Появляется журнал вопросов сотрудников.
Технические средства заложены, организационное решение за заказчиком.

## Открытые вопросы

1. **Эксплуатируется ли MariaDB в компании уже?** Если её заводят специально
   под Keycloak, преимущество исчезает и ровнее взять PostgreSQL. Вопрос задан,
   ответа нет.
2. **Есть ли работающий корпоративный SSO и настроена ли федерация с AD?**
   От этого зависит объём настройки Keycloak.
3. **Имя административной группы** и кто в неё входит.
4. **Срок хранения диалогов** — 90 дней взяты как разумное значение
   по умолчанию, требует подтверждения.
