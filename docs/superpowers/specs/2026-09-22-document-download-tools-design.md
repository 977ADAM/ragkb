# Выдача оригиналов документов через инструмент чата

Статус: согласована для подготовки плана 2026-09-22. Реализация не начата.

## Цель и согласованные требования

Чат отвечает по документам корпуса и может приложить существующий оригинал
для скачивания: по прямой просьбе или когда технические требования полезны
при подготовке рекламных материалов. Генерация новых файлов не входит в задачу.

Все документы, включая `Interpool_База_знаний_продукты_FAQ_2026_09_10.docx`,
остаются доступны для поиска, ответов и цитирования фрагментов. Скачивание
оригинала базы знаний выключено. Для PDF AdSmart Multi, HTML5, MediaText,
MediaText Premium, Mobile HTML5 и Mobile Slider разрешение можно включить.
Наличие файла в data/docs не заменяет загрузку через интерфейс и регистрацию.

Пользователь подтвердил:

- настоящий инструмент `get_download_link`;
- все используемые модели поддерживают tool calling;
- переключатель «Разрешить скачивание оригинала» при загрузке и в списке;
- значение по умолчанию — выключено;
- ответы и фрагменты закрытых для скачивания документов остаются доступны.
- управление намеренно открыто всем посетителям, включая изменение
  разрешения на скачивание; отдельные роли и ограничения не требуются.

## Граница разрешения

`download_allowed` разрешает выдачу оригинала и не влияет на поиск/цитаты.
Проверка выполняется как при вызове инструмента, так и при HTTP-скачивании.
Запрещённый оригинал нельзя получить прямым запросом при выключенном флаге.

Управление намеренно доступно всем посетителям — пользователь подтвердил
этот контракт. Любой посетитель может изменить флаг. Это настройка
публикации оригинала; сервер соблюдает её актуальное значение независимо
от того, кто его установил. Авторизацию, роли, отдельные ограничения на
редактирование флага и неизменяемый запрет для конкретного DOCX не добавляем.

## Варианты и выбранное направление

1. Кнопка скачивания у каждого разрешённого источника — проще, но не выполняет
   требование самостоятельного вызова инструмента агентом.
2. Инструмент с проверкой реестра и структурированными вложениями — выбранный
   вариант: соответствует запросу и сохраняет серверный контроль.
3. Отдельное хранилище/индекс для раздаваемых файлов — сейчас избыточно:
   документы уже зарегистрированы и нужны тому же поиску.

## Реестр и жизненный цикл

Добавить `document_id` (уникальный UUID, строковое представление) и
`download_allowed` (boolean, default false). Имя остаётся существующим
ключом для совместимости операций загрузки и удаления. ID используется
в новых маршрутах, инструменте и вложениях и не является секретом.

Нужна новая добавочная миграция после 0001: заполнить уникальные ID у
существующих записей и установить false. Не переписывать 0001, не возвращать
исторические миграции и не затрагивать старые таблицы аккаунтов/переписки.
Это расширяет текущее правило «одна начальная миграция» новой фичей;
при реализации актуализировать AGENTS.md и README.

Изменение разрешения применяется сразу, без переиндексации. Разрешение
читается из реестра, а не из потенциально устаревших метаданных векторов.
При замене файла с тем же именем ID сохраняется; разрешение берётся из
явного параметра загрузки, при его отсутствии сбрасывается в false.
Интерфейс явно показывает выбор при подтверждении замены.
После удаления ID перестаёт работать; повторная загрузка создаёт новый ID.
Ссылка указывает на текущую версию документа, не на исторический снимок.

## Поиск кандидатов

Привязать источники retrieval к зарегистрированным документам, получая ID
и разрешение из реестра через прикладной слой. Не передавать инструменту
произвольные файловые пути. Полный DOCX в контекст не добавляется:
сохраняется существующий поиск по фрагментам.

Прямой запрос файла не должен зависеть только от попадания его фрагмента
в top-k: прикладной слой дополнительно ищет кандидатов по именам разрешённых
документов. Сначала точное совпадение названия, затем нормализованное
сопоставление слов; сходные desktop/mobile и Premium варианты не объединять.
Кандидаты передаются модели с ID и именами. Инструмент принимает только ID
кандидатов текущего запроса и повторно проверяет реестр.

Это позволяет приложить PDF, даже если фактический ответ основан на DOCX.
Поиск содержимого, доступность LLM и существующие ограничения индекса
сохраняются; отдельный файловый ассистент без рабочего RAG не входит в задачу.

## Инструмент и выполнение

Вход `get_download_link`: `{document_id: string}`.
Успех: `{document_id, filename, url, media_type, size}`.
URL — относительный адрес BFF `/api/documents/{document_id}/download`.
Отказ: структурированный код `not_available`, без файловых путей.
Результат недоступности не должен обрывать полезный текстовый ответ.

LangChain tool binding и обработка сообщений модели остаются в core.
Core не импортирует services, domain, db или api: использует внедряемый
callback/порт с простыми типами. Прикладной слой разрешает документы через
реестр, а db отвечает только за хранение. Нельзя вызывать асинхронный
реестр через вложенный asyncio.run в работающем event loop; контракт
исполнения инструмента должен корректно поддерживать асинхронный I/O.

Вместо потери tool calls в StrOutputParser для этого сценария нужен
цикл модель → вызовы → результаты → модель. Цикл живёт только в одном
запросе; сообщения инструментов и переписка между запросами не сохраняются.
Предлагаемый предел: 3 раунда, до 8 вызовов за запрос, без повторного
исполнения одинакового ID. Неизвестный инструмент и некорректные аргументы
дают контролируемый отказ. При исчерпании лимита завершить с предупреждением.

Текст модели передаётся событиями token, аргументы и внутренние сообщения
инструментов пользователю не стримятся. Частичные tool-call chunks нужно
собрать до исполнения. Успешные вложения накапливаются на сервере отдельно
от текста модели и дедуплицируются по ID. Если последующая генерация
оборвалась, сохраняются уже полученные вложения, а done отражает обрыв.
Неподдерживаемый сервером tool calling — явная ошибка, не подмена инструментов
распознаванием выдуманных ссылок в тексте.

## Политика предложения файлов

- «Пришли требования к AdSmart Multi»: вызвать инструмент и приложить PDF.
- «Что подготовить для размещения AdSmart Multi»: ответить и предложить PDF
  через инструмент, если кандидат однозначен.
- Узкий вопрос о конкретном параметре: ответ с цитатой; вложение необязательно.
- Неоднозначный формат: не выбирать случайный файл, попросить уточнение.
- Запрос оригинала запрещённого документа: не выдавать файл, предложить
  ответ или фрагмент по вопросу.

Каждый вопрос независим. Поэтому при уточнении предлагать полную формулировку
следующего запроса, например «Пришли требования к AdSmart Mobile HTML5».
Не обещать понимание одиночного ответа «мобильный» без истории.
Инструкции внутри документов не могут изменять разрешения или политику tools.

## HTTP и потоковый контракт

Новые/расширенные API:

- список документов: добавить ID и download_allowed;
- загрузка: необязательный boolean download_allowed=false;
- PATCH `/api/v1/documents/{document_id}/download-permission` с телом
  `{download_allowed: boolean}`; вернуть ID и актуальное разрешение;
- GET `/api/v1/documents/{document_id}/download`: бинарный оригинал.

BFF имеет соответствующие маршруты без `/v1`. Скачивание проксируется
потоком без JSON-разбора и полной буферизации; сохраняются Content-Type
и Content-Disposition. Заголовок attachment корректно поддерживает
русские имена. Ответы файлов и отказов используют Cache-Control: no-store.

Отсутствующий документ, выключенное разрешение или отсутствующий файл — 404.
Без реестра выдача невозможна. Путь разрешается только по записи реестра:
проверка выхода за docs_dir и симлинков обязательна, никакого произвольного
path из аргументов модели или URL. Не монтировать data/docs как static.
Отзыв разрешения блокирует будущие запросы, но не отзывает уже скачанные
файлы или начавшуюся передачу.

В done добавить `attachments: list[Attachment]`, по умолчанию [].
Поля Attachment: document_id, filename, url, media_type, size.
Источники остаются отдельно в sources и не подразумевают скачивание.
Описать DTO инструмента, вложений, изменяемого разрешения и событий
token/done; OpenAPI должен указывать NDJSON для /ask. Общая переработка
всех существующих API-схем не входит в задачу.

## Интерфейс

В загрузке — выключенный по умолчанию переключатель, применяемый к новой
пачке. В списке — состояние и переключатель у каждого зарегистрированного
документа, с блокировкой на время сохранения и явной ошибкой при отказе.
Не включать разрешения автоматически по расширению, папке или имени.

В ответе — карточки файлов с именем, размером и кнопкой «Скачать», в том
числе если текст пуст, но инструмент успешно выдал файл. Карточки строятся
из attachments, а не Markdown-ссылок модели. При удалённом документе или
отозванном разрешении показать понятный отказ и сохранить текст ответа.
Копирование ответа и модалка источников сохраняют прежнее назначение.
Очистка чата удаляет карточки из памяти страницы вместе с сообщениями.

## Наблюдаемость и ограничение скачиваний

### Журнал действий

Рекомендованное дополнение по замечанию пользователя, не отдельная система
аудита и не требование вводить аккаунты. Текущий access-лог содержит метод,
путь, статус и длительность, но не старое/новое разрешение и адрес клиента.

Добавить структурированные события изменения разрешения (включая загрузку
и замену файла) и попыток скачивания. Поля: время UTC, request_id,
document_id, действие, результат; для изменения — старое и новое значение.
Фиксировать изменение после успешного сохранения. Скачивание различает
отказ, начало передачи, завершение и обрыв; успешная передача сервером
не доказывает сохранение файла пользователем. Выдача ссылки инструментом
сама по себе не считается скачиванием. При возможности учитывать число
переданных байтов без буферизации файла.

На внешней HTTP-границе фиксировать IP и связывать запрос с backend через
request_id, сформированный доверенной стороной. Без авторизации IP означает
источник запроса, а не установленную личность; несколько посетителей могут
иметь один адрес. Не писать тексты вопросов, содержимое документов и секреты.
Использовать существующую ротацию логов; отдельная таблица аудита и UI не нужны.

### Ограничение скачивания

Ограничивать реальный маршрут передачи файла, а не только вызов инструмента.
В текущем Compose опубликован frontend:3000, конфигурации Angie в репозитории
нет. Поэтому базовая защита должна работать на BFF и при прямом доступе к
этому порту, без обязательного внешнего reverse proxy.

Предлагаемые стартовые значения: 10 запросов в минуту на IP с коротким
всплеском до 3 запросов; не более 2 одновременно передаваемых файлов на IP.
Значения конфигурируемые, чтобы учитывать общий NAT корпоративной сети.
Применять проверку до запроса бинарного тела у backend; учитывать HEAD,
повторные/Range-запросы и неуспешные попытки, чтобы они не обходили лимит.
Освобождать слот передачи при завершении, отмене и ошибке потока.
Отказ — 429 с Retry-After, без запроса файла; UI показывает возможность
повторить позже. Лимит не затрагивает поток чата и чтение фрагментов.

Для одного процесса frontend допустимо ограниченное по размеру хранилище
счётчиков в памяти с удалением истёкших записей. Это лимит одного процесса:
при нескольких репликах нужен общий limiter или единая внешняя точка
ограничения, а не независимые счётчики, выдаваемые за глобальную защиту.
Backend в Compose не публикуется напрямую; при изменении схемы развёртывания
нельзя оставлять обходной публичный маршрут без эквивалентного ограничения.

IP получать из соединения либо из заголовка только от настроенного
доверенного прокси. Не доверять произвольному X-Forwarded-For из браузера.
Документировать настройку цепочки Angie → BFF и проверять, что посетители
не сводятся к одному адресу прокси и не могут подменить ключ ограничения.

Частота и параллелизм снижают нагрузку, но не задают потолок байтов трафика.
Если потребуется жёсткий бюджет трафика, добавить отдельную квоту байтов
или ограничение скорости на внешнем прокси; не обещать этого от per-IP RPS.

## Проверки и критерии приёмки

1. Миграция работает на SQLite и Postgres, сохраняет записи и чужие таблицы;
   все прежние документы закрыты для скачивания, ID уникальны и стабильны.
2. Выключенный DOCX доступен retrieval/цитатам, но не tool/HTTP-скачиванию.
3. Разрешённый зарегистрированный PDF выдаётся по прямой просьбе; байты
   совпадают с оригиналом, корректны имя, MIME и маршрутизация через BFF.
4. Файл вне реестра не выдаётся; закрытый/удалённый/пропавший файл, traversal,
   выход через симлинк и выдуманный ID не дают доступа к данным.
5. Флаг действует без переиндексации; отзыв блокирует старую ссылку;
   повторная загрузка и замена соблюдают описанную семантику.
6. ScriptedChatModel воспроизводит настоящий tool call и продолжение;
   проверить фрагментированные аргументы, несколько вызовов, дедупликацию,
   отказ, лимит раундов, обрыв модели и обычный ответ без инструмента.
7. Файловый кандидат находится по имени, даже когда top-k содержит DOCX;
   неоднозначные варианты не приводят к случайному вложению.
8. Frontend корректно показывает attachments, переключатель, ошибку
   скачивания и существующие источники; старое done без attachments допустимо.
9. Существующие backend/frontend проверки и архитектурные тесты проходят.
   Реальный запуск с настроенной tool-capable моделью проверяется отдельно
   от детерминированных тестов, если сервер доступен.
10. Для журнала проверить успешное/отклонённое изменение флага, выдачу ссылки
    без скачивания, завершение/обрыв передачи и отсутствие содержимого
    документов в записях; события BFF/backend связываются request_id.
11. Для лимита проверить 429/Retry-After, восстановление после окна, разные
    IP, общий NAT, подмену forwarded-заголовков, повторные/Range-запросы,
    освобождение слотов после отмены и отсутствие обращения к файлу при 429.

## Следующий этап

Проверка этой спецификации пользователем, затем план реализации. Документ
не разрешает сам по себе публикацию каких-либо существующих файлов:
разрешения остаются выключены до явного изменения через управление.
