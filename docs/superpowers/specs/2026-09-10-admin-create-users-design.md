## Зачем

Публичная регистрация открывает контур любому, кто знает URL. Корпус и
диалоги — корпоративные: людей заводит администратор, вход остаётся
формой `/login`.

Эта спека снимает решение «публичный signup остаётся» из
`2026-09-02-admin-users-design.md`. Исторические планы в
`docs/superpowers/plans/` не трогаем.

## Границы

**В работе:** `POST /api/v1/auths/signup` всегда 403; страница `/register` без
формы; форма создания на `/admin/users`; `POST /api/v1/admin/users`
(имя, пароль, роль); BFF; тесты; живые доки (README, AGENTS, OpenAPI).

**Вне работы:** сброс чужого пароля; письма и приглашения; удаление маршрутов
signup/`/register` (пути остаются, чтобы старые закладки не давали 404);
правки обрубка `GET /users`; отдельная обработка `proxy`/`disabled` (локальных
учёток там нет, signup всё равно 403); сидер `ensure-admin`.

## Ключевые решения

1. **Signup не удаляем — закрываем.** Путь и BFF остаются. Без сессии
   ручка по-прежнему в исключениях (иначе был бы 401). Ответ всегда 403
   `{"detail": "регистрация закрыта, учётку создаёт администратор"}`. Тело
   не разбираем: даже валидные поля пользователя не создают. Куку не ставим.
2. **Админ задаёт имя и пароль.** Новый человек входит на `/login` и при
   желании меняет пароль в `/profile`. Сессию админа не трогаем: новому
   пользователю куку не выдаём.
3. **Роль в форме создания.** `user` или `admin`, по умолчанию в UI — `user`.
   Правило «нельзя снять/удалить последнего админа» на создание не
   распространяется: завести второго админа можно.

## HTTP

Префикс FastAPI `/api/v1`, BFF без версии. Все `/admin/*` — сессия, затем
`require_admin`.

| Метод | Путь | Поведение |
|---|---|---|
| `POST` | `/auths/signup` | всегда 403, без записи в БД, без `Set-Cookie` |
| `POST` | `/admin/users` | `{ "username", "password", "role" }` → **201** `{ "username", "role", "created_at" }` |
| `GET`/`PATCH`/`DELETE` | `/admin/users`… | без изменений |

`role` только `user` или `admin`. Логин: lower+trim, 3–32, `[a-z0-9._-]`.
Пароль: 8–128. Те же pydantic-ограничения, что у бывшего signup
(`Credentials` + поле `role`). Занятый логин — **409** (`Conflict`, как
`create_user`). Невалидное тело — 422. Не-админ — 403.

BFF: `POST /api/admin/users` проксирует на FastAPI; `POST /api/auths/signup`
проксирует 403 как есть.

`AuthService.register` с HTTP больше не вызывается. Создание — метод
`AdminUsersService` (хеш Argon2, `create_user(..., role=...)`, без сессии).

## UI

`/admin/users`: над таблицей форма «Создать» — имя, пароль, выбор роли
(`user` по умолчанию), кнопка. Успех — строка в списке, поля пустые. Ошибки
тем же текстом, что смена роли.

`/register`: публичная (хук `PUBLIC` без изменений по составу путей). Без
полей. Текст, что учётку создаёт администратор, ссылка «Войти» на `/login`.

`/login`: ссылка «Регистрация» ведёт на `/register`.

`/profile` и смена своего пароля — без изменений.

## Сидер

`ensure-admin` без изменений: первый админ из `ADMIN_LOGIN` /
`ADMIN_PASSWORD`. Compose и `make api` от этого не зависят иначе, чем сейчас.

## Тесты

- `POST /api/v1/auths/signup` → 403; пользователя с этим логином нет; заголовок
  `Set-Cookie` нет.
- Админ `POST /api/v1/admin/users` с `role=user` и `role=admin` → 201, строка
  в `GET /admin/users`.
- Не-админ на `POST /admin/users` → 403.
- Занятый логин → 409; короткий пароль / плохой логин / чужая роль → 422.
- После создания админская сессия жива (тот же `/auths/me`).

Фикстуры, которые сейчас заводят людей через signup, перевести на
`create_user` или на `POST /admin/users` под админом.

## Согласованность

Не добавляет миграцию: `users.role` уже есть. Не открывает signup в
`disabled` «для удобства тестов». Не переписывает планы. README/AGENTS:
вход через `/login`, людей заводит админ; `POST /auths/signup` в таблице
API — закрыт.
