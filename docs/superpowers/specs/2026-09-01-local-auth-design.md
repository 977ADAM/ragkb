## Зачем

Нужен вход в приложение логином и паролем внутри ragkb. Корпоративный SSO
(Angie + Keycloak) для этого захода не используется: один способ войти —
форма в интерфейсе. Личность по-прежнему строка `User.name`, к ней уже
привязаны диалоги.

## Границы

**В работе:** слайс `features/auth` (регистрация, логин, выход, `GET /auth/me`);
таблицы пользователей и сессий в SQLite через Alembic; кука сессии; `current_user`
читает сессию при `auth.mode: session`; BFF-прокси `/api/auth/*` и проброс
`Cookie`; страницы `/login` и `/register`; редирект без сессии; имя и «Выйти»
в шапке; тесты; зависимость для хеша пароля; правки README / AGENTS / `.env.example`
под новый режим.

**Вне работы:** SSO и кнопка «войти через компанию»; склейка аккаунтов с
Keycloak; email, группы, роли, админка, сброс пароля, «запомнить меня»;
профиль и настройки; разграничение документов; правки конфига Angie в этом
репозитории (Angie живёт на сервере вне compose — оператор снимает обязательный
OIDC с путей фронта, иначе до форм не дойти); JWT; токен в `localStorage`.

«Перестроить индекс» по-прежнему требует группу `ragkb-admins` в объекте
`User`. У локального пользователя групп нет — кнопки не будет, пока отдельная
работа не задаст роль.

## Режим аутентификации

Новое значение `auth.mode: session` (конфиг и `RAGKB_AUTH_MODE`).

| Режим | Поведение |
|---|---|
| `session` | Личность только из валидной сессионной куки. Иначе 401, кроме исключений ниже |
| `disabled` | Как сейчас: пользователь `anonymous`. Тесты и `make backend` |
| `proxy` | Как сейчас: заголовки `X-Forwarded-*`. В этом заходе прод на него не переводим |

Исключения без сессии в режиме `session`: `GET /health`, `POST /auth/register`,
`POST /auth/login`. Остальное, включая `GET /bootstrap` и `GET /auth/me`, —
с сессией (me без куки — 401).

Локальный compose: `RAGKB_AUTH_MODE=session` у `rag`; `RAGKB_DEV_USER` для
личности не используется. `make backend` может остаться на `disabled`, чтобы
не ломать привычный цикл без форм; проверка входа — pytest и `make up` /
ручной заход на `/login`.

## Хранение

Тот же файл SQLite, что `history.path` (`RAGKB_HISTORY_PATH`). Аккаунты нужны
и при `history.enabled: false`: эфемерные диалоги не отменяют таблицу
пользователей. Адаптер слайса открывает этот файл сам, через `sqlite3`, без
SQLAlchemy в пакете `ragkb`.

Ревизия Alembic `0004_…` после `0003_message_model`. Код истории по-прежнему
проверяет ровно одну ожидаемую ревизию — её нужно сдвинуть на `0004`.

`users`: `id` TEXT PK (UUID), `username` TEXT UNIQUE NOT NULL (канонический
вид: trim и нижний регистр), `password_hash` TEXT NOT NULL, `created_at` TEXT
NOT NULL (UTC).

`sessions`: `token_hash` TEXT PK (SHA-256 от секрета куки), `user_id` TEXT NOT
NULL REFERENCES `users(id)` ON DELETE CASCADE, `expires_at` TEXT NOT NULL.

Секрет куки в базе не хранится. Просроченные сессии можно не вычищать
фоном в этом заходе: при чтении истекшая строка — как отсутствие сессии.

Пароль: Argon2 (зависимость `argon2-cffi` у пакета). Длина пароля 8–128
символов. Логин при регистрации: 3–32 символа, после нормализации совпадает с
`[a-z0-9._-]`.

## HTTP

Форма ошибки не меняется: `{"detail": "..."}`.

| Метод и путь | Тело | Успех |
|---|---|---|
| `POST /auth/register` | `{username, password}` | 200 `{username}` и `Set-Cookie`; сразу сессия |
| `POST /auth/login` | `{username, password}` | то же |
| `POST /auth/logout` | нет | 204, снять куку, удалить сессию |
| `GET /auth/me` | нет | 200 `{username}` |

Кука: имя `ragkb_session`, `HttpOnly`, `Path=/`, `SameSite=Lax`. `Secure` —
если запрос HTTPS или `X-Forwarded-Proto: https`. Срок — 7 суток. Значение —
случайные непрозрачные байты (не JWT).

Занятый логин при регистрации — 409. Неверный логин или пароль при входе —
401 с одним и тем же `detail`, без различия «нет пользователя» / «плохой
пароль». Невалидное тело — 422 (pydantic), как у остальных ручек.

Повторный `register`/`login` при уже живой сессии: старую сессию удалить,
выдать новую (в том числе при входе в другую учётку).

Слайс подключается в `create_app` рядом с остальными. Контейнер отдаёт порт
хранилища аккаунтов.

`current_user` в режиме `session` не читает `X-Forwarded-Preferred-Username`
как личность: подделка заголовка до FastAPI не должна становиться пользователем.

## BFF и интерфейс

Маршруты: `frontend/src/routes/api/auth/register`, `login`, `logout`, `me` —
прокси на бэкенд с пробросом `Cookie` и `Set-Cookie`. Браузер к FastAPI не
ходит.

Все клиентские `fetch` на `/api/…` — `credentials: 'include'`.

Страницы `/login` и `/register`: по форме на страницу, ссылка на соседнюю.
Без сессии любой другой UI-маршрут (кроме этих двух) — редирект на `/login`.
После успешного register/login — `/new`. В шапке: `username` и кнопка
«Выйти» (`POST /api/auth/logout`, затем `/login`).

Проверка сессии для раскладки: `GET /api/auth/me` (или поле `user` из
bootstrap после me). Не смешивать с `RAGKB_DEV_USER`.

## Тесты

- регистрация пишет пользователя и отдаёт куку;
- повтор того же логина — 409;
- короткий пароль / плохой логин — 4xx, пользователя нет;
- логин с верным и неверным паролем;
- запрос с чужой или пустой кукой — 401 на защищённой ручке;
- logout гасит сессию;
- после входа `GET /bootstrap` — 200 и `user.name` равен логину;
- архитектурный тест: в `backend/ragkb/` нет импорта sqlalchemy (как сейчас).

Существующие тесты с `auth.mode: disabled` не обязаны ходить через формы.

## Риски

Открытая регистрация в LAN: любой, кто видит URL, заводит аккаунт. Это
осознанно для этого захода.

Angie, если оставить обязательный OIDC, сделает формы недостижимыми. Снятие
OIDC с фронта — шаг выкладки, не код репозитория.

Смена `EXPECTED_REVISION` в адаптере истории должна выйти в одном релизе с
миграцией `0004`, иначе процесс не поднимется до `alembic upgrade head`.
