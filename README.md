# ragkb — RAG-система над базой знаний

Вопрос-ответ по корпоративным документам (PDF, DOCX, MD, TXT, HTML) с обязательными
ссылками на источники. Систему можно развернуть on-premise: для этого адреса
эмбеддингов, генерации и реранкера должны вести на сервисы внутри вашего контура.

## Что внутри

```
документы → парсинг → секции → чанки → эмбеддинги ─┐
                                       └──→ BM25 ──┤
                                                   ├→ RRF → MMR/реранк → промпт → LLM → ответ + ссылки
                                    запрос ────────┘
```

Ядро собрано на **LangChain**: цепочка ответа — LCEL (`prompt | ChatOpenAI |
StrOutputParser`), ретриверы, сплиттер и хранилище — его же объекты. Наружу это
не выходит: `core/ports.py` описывает `AnswerEngine`, а прикладной слой
(`api/`, `services/`) LangChain не импортирует — правило закреплено тестом
`tests/test_architecture.py`.

Ключевые решения и почему они такие:

| Решение | Причина |
|---|---|
| **Гибридный поиск** (BM25 + векторы) | Векторы ловят перефразировки, BM25 — точные сущности: номера приказов, артикулы, аббревиатуры. По отдельности каждый заметно проваливается. |
| **Слияние через RRF**, а не сумму оценок | BM25 выдаёт 0…30, косинус 0…1 — складывать их нельзя. RRF работает с рангами и не требует калибровки. |
| **Чанк несёт путь заголовков** | Запрос «срок оплаты отпуска» найдёт абзац, где слово «отпуск» есть только в заголовке раздела. |
| **Стемминг для русского** | «отпуска», «отпуску», «отпуском» — для BM25 это три разных токена без нормализации. |
| **MMR в выдаче** | Иначе top-5 часто оказывается пятью вариациями одного абзаца, и модель не видит альтернатив. |
| **Обязательные ссылки [N]** | Проверяемость ответа сама по себе снижает выдумывание и позволяет пользователю дойти до первоисточника. |
| **ChromaDB как хранилище** | HNSW-индекс, персистентность из коробки, фильтры по метаданным; в LangChain это `langchain-chroma`, поэтому точечное удаление документа осталось. |
| **Генерация обязательна** | Экстрактивного ответа «из найденных фрагментов» больше нет: без настройки генерации вопрос отклоняется с 503 до открытия потока. Сбои во время генерации передаются в завершающем событии потока. |

## Хранилище

Основной бэкенд — **ChromaDB** во встроенном режиме через `langchain-chroma`:
отдельный сервис поднимать не нужно, база лежит файлами в `data/index/chroma`.
При необходимости переключается на отдельный сервер Chroma (`store.chroma_host`).
Второй бэкенд — `memory` (`InMemoryVectorStore` из langchain-core): он нужен
тестам, чтобы не зависеть от chromadb и диска.

Два решения, которые стоит знать:

- **Метрика — cosine, а не L2 по умолчанию.** Коллекция создаётся с
  `hnsw:space: cosine`, и близость согласуется с порогом `retrieval.min_score`.
- **Векторы считает эмбеддер LangChain** (`langchain-ollama`), а хранилище
  только складывает готовые — своей embedding-функции у коллекции нет.

BM25 остаётся нашим: `langchain_classic.retrievers.BM25Retriever` — это шим на
устаревший `langchain-community`, поэтому лексическая половина реализована как
`LexicalRetriever(BaseRetriever)` на `rank-bm25` с русской токенизацией.
Слияние с плотным поиском делает `EnsembleRetriever` (RRF), а не свой код.

HNSW — приближённый поиск. Полноту поиска проверяйте на своём корпусе с
`backend/examples/eval.py`; параметр `store.hnsw_search_ef` позволяет менять
соотношение полноты и скорости.

## Быстрый старт

Нужны Python 3.10+, uv, Bun и работающая Ollama. Авторизации, аккаунтов и
истории нет: чат, документы и настройки доступны всем посетителям.
Переписка живёт в памяти страницы и исчезает после обновления; каждый вопрос
обрабатывается независимо.

Локальный запуск с SQLite, из корня репозитория:

```bash
make sync
make sync-frontend
mkdir -p data
export RAGKB_DATABASE_URL=sqlite+aiosqlite:///data/ragkb.db
export RAGKB_EMBEDDING_URL=http://127.0.0.1:11434
export RAGKB_EMBEDDING_MODEL=qwen3-embedding:0.6b
export RAGKB_LLM_URL=http://127.0.0.1:11434/v1
export RAGKB_LLM_MODEL=qwen2.5:7b-instruct
ollama pull qwen3-embedding:0.6b
ollama pull qwen2.5:7b-instruct
make migrate
make api
```

В другом терминале из корня репозитория: `make frontend`, затем открыть
`http://localhost:5173`. Загрузить документы на `/admin/documents`; интерфейс
после загрузки очереди перестроит индекс. Для повторной пересборки есть кнопка.
Файлы, скопированные прямо в `data/docs`, в корпус не попадают.

Вместо SQLite можно задать `RAGKB_DATABASE_URL` вида
`postgresql+asyncpg://user:password@127.0.0.1:5432/ragkb`. Базу нужно создать
заранее, затем выполнить `make migrate`. Без подключения к БД загрузка,
удаление документов и пересборка возвращают 400 с подсказкой о настройке БД.

Корневой `.env` читается независимо от рабочего каталога для подключения к
БД (`RAGKB_DATABASE_URL` и `POSTGRES_*`). Остальные именованные переменные
`RAGKB_*`, в том числе адреса моделей и пути к данным, текущий код берёт из
**окружения процесса**. Поэтому локально используйте `export`, как выше,
либо экспортируйте значения своего shell-совместимого `.env` перед запуском:

```bash
set -a
. ./.env
set +a
```

В Compose `env_file: .env` экспортирует значения автоматически. Пример
`.env.example` рассчитан на Compose: локально замените адреса
`host.docker.internal` на `127.0.0.1`, задайте локальную БД и локальные пути
к данным, если они переопределены.

Эмбеддинги требуют корня Ollama без `/v1`, генерация — OpenAI-совместимого
API с `/v1`. Без адреса генерации `POST /api/v1/ask` возвращает 503;
экстрактивного ответа нет. При отказе Ollama во время индексации возвращается
503 с описанием причины. Настройки из `/admin/settings` сохраняются файлом
и имеют приоритет над окружением.

## Боевая конфигурация

Compose запускает Postgres, миграции, backend и frontend. Сервис создания
администратора отсутствует. Postgres используется для реестра документов.

```bash
cp .env.example .env
# Задайте параметры БД, адрес Ollama и адрес OpenAI-совместимого LLM в .env.
ollama pull qwen3-embedding:0.6b
ollama pull qwen2.5:7b-instruct
docker compose up -d --build
```

Интерфейс доступен на порту 3000. Внешний Angie при использовании должен
проксировать сайт на frontend без прежних правил входа и OIDC.

Эмбеддинги считает сервис вне образа. По умолчанию это Ollama: контейнер `rag`
обращается к ней по `host.docker.internal:11434` (адрес задан в `Dockerfile` и
перекрывается `RAGKB_EMBEDDING_URL`). Сервиса Ollama в Compose нет — модели
остаются под управлением `ollama pull`, а образ `rag` не тащит torch и веса
эмбеддера. Вместо Ollama можно указать любой OpenAI-совместимый сервер
(`RAGKB_EMBEDDING_BACKEND=openai` и адрес с `/v1`, например llama.cpp в режиме
`--embedding` на своём порту): тогда каталог моделей берётся из его `/v1/models`.
Модель должна поддерживать пулинг — llama.cpp отдаёт `/v1/embeddings` только
при пулинге, отличном от `none` (для моделей на среднем пулинге это
`--pooling mean`).
Генерация — OpenAI-совместимый HTTP (`RAGKB_LLM_URL`, обычно корень `…/v1`);
на неё можно указать и саму Ollama.
Каталог `./data/docs` смонтирован на запись для загрузки документов через UI.
Смена модели эмбеддингов (как и её размерности) требует перестроения индекса:
движок отказывается искать векторами другой модели, а не выдаёт молча мусор.

### Миграции

В репозитории одна ревизия — `0001_corpus_documents`. Она создаёт реестр
сразу в полном виде: имя, `document_id` (адрес выдачи оригинала),
`download_allowed` (разрешение выдать оригинал, по умолчанию выключено) и
`index_enabled` (участие в поиске, по умолчанию включено).

```bash
make migrate
```

Для Compose схема накатывается сервисом `migrate`, который поднимается
автоматически: `docker compose up -d --build postgres migrate rag frontend`.
Приложение само схему не накатывает.

**Если база уже существовала** на прежних ревизиях (их в каталоге больше нет),
есть два пути:

1. **Пересоздать базу** — если данные реестра не нужны. Документы лежат в
   `data/docs`, после обновления их загружают заново через страницу
   «Документы» (файлы на диске при загрузке перезаписываются теми же именами):

   ```bash
   docker compose down -v && docker compose up -d --build postgres migrate rag frontend
   ```

2. **Пометить базу начальной ревизией** — если столбцы `document_id`,
   `download_allowed` и `index_enabled` в таблице уже есть:

   ```bash
   uv run --project backend alembic -c backend/alembic.ini stamp --purge 0001_corpus_documents
   ```

   `--purge` обязателен: прежних ревизий в каталоге версий нет, и обычный
   `stamp` не сможет разрешить текущее значение в `alembic_version`.

Старые таблицы аккаунтов, сессий, диалогов и оценок миграция не читает, не
заполняет и автоматически не удаляет: если они есть в базе, остаются как были.

### Выбор моделей

**Эмбеддинги.** По умолчанию — Ollama и `qwen3-embedding:0.6b`. Второй
рабочий бэкенд — `openai`: любой OpenAI-совместимый HTTP-сервер
(`POST {embedding.base_url}/embeddings`), то есть llama.cpp, vLLM, TEI.
У Ollama адрес — корень API без `/v1`, у `openai` — корень с `/v1`; ключ
(`RAGKB_EMBEDDING_API_KEY`) нужен только второму и локальными серверами
обычно не проверяется.

На `/admin/settings` поле модели получает варианты у выбранного бэкенда:
у Ollama — из её каталога, у `openai` — из `GET {base_url}/models`.
Каталог Ollama по возможности отбирает модели с поддержкой эмбеддингов и
показывает размерность и объём модели. После `ollama pull` нажмите «Обновить
список моделей». Если сервер не сообщает возможности моделей, список может быть
шире. Смена бэкенда, модели или размерности требует полной пересборки индекса.

**Генерация.** Модель выбирается в чате из каталога. Если доступны сведения
о возможностях, модели, умеющие только эмбеддинги, из списка исключаются.
`llm.backend` выбирает источник каталога (`openai`, `ollama`, `static`),
а генерация всегда идёт через `ChatOpenAI` по OpenAI-совместимому HTTP.

**Реранкер.** Поддерживается внешний HTTP-сервис: `retrieval.reranker: http`
и `retrieval.reranker_url` (Jina/Cohere-совместимый `/rerank`). Локального
cross-encoder нет. Оценивайте эффект и задержку на своём наборе вопросов.

## Команды

Консольной точки входа больше нет. Сервер — uvicorn, индекс — `POST /api/v1/index/rebuild`,
оценка поиска — `python backend/examples/eval.py`.

## HTTP API

Браузер ходит только через BFF SvelteKit: `/api/ask` → `/api/v1/ask`.
Все маршруты открыты, cookie и заголовки идентификации не используются.

| Метод | Назначение |
|---|---|
| `GET /health` | Живость и наличие индекса |
| `GET /api/v1/status` | Сведения об индексе и моделях |
| `GET /api/v1/bootstrap?session_id=` | Версия, организация, модели и индекс; UUID вкладки для телеметрии |
| `GET /api/v1/models` | Каталог моделей генерации |
| `GET /api/v1/organization` | Сведения об организации, 404 если не настроена |
| `POST /api/v1/search` | Поиск без генерации |
| `POST /api/v1/ask` | Независимый вопрос, ответ потоком NDJSON |
| `POST /api/v1/events` | Телеметрия, до 100 событий |
| `POST /api/v1/index/rebuild` | Перестроение индекса |
| `GET /api/v1/admin/organization` | Организация и ссылки управления |
| `GET /api/v1/admin/reports` | Заглушка отчётов: `status: unavailable` |
| `GET /api/v1/admin/settings` | Поля настроек: значения, источники, требования |
| `PUT /api/v1/admin/settings` | Правка настроек и сброс переопределений |
| `GET /api/v1/admin/documents` | Файлы, состояние индексации, `document_id`, `download_allowed` и `index_enabled` |
| `POST /api/v1/admin/documents` | Multipart-загрузка; `?index=false` откладывает индексацию, `?download_allowed=true` открывает оригинал, `?index_enabled=false` исключает из поиска |
| `DELETE /api/v1/admin/documents/{name}` | Удаление файла и записи индекса |
| `PATCH /api/v1/documents/{document_id}/download-permission` | Разрешение на выдачу оригинала |
| `PATCH /api/v1/documents/{document_id}/index-permission` | Участие документа в поиске |
| `GET`, `HEAD /api/v1/documents/{document_id}/download` | Оригинал документа, если разрешение включено |

Актуальная схема FastAPI доступна на `/openapi.json`, интерактивное описание —
на `/docs` бэкенда. Старая Auth API-спецификация в `docs/` архивная.

Тело вопроса: `question` (не менее двух символов после удаления пробелов по краям), необязательные `model`, `top_k` (1–20), `expand`.
Модель проверяется по каталогу. История, идентификатор диалога и пользователя
не принимаются. Ответ завершается событием done с источниками; при обрыве
после первого токена `truncated` истинно. Если генерация не настроена, запрос
отклоняется с 503 до открытия потока. При отказе модели до первого токена
поток завершается с предупреждением и `truncated: false`.

В потоке ровно два вида строк — `token` и `done`. Оригиналы документов, которые
модель приложила вызовом инструмента, приходят в `done.attachments`; отдельными
строками они не идут, карточки в интерфейсе строятся по этому списку.

```json
{"type":"token","text":"Ежегодный "}
{"type":"done","sources":[],"warnings":[],"elapsed_sec":0.2,"model":"qwen2.5:7b-instruct","truncated":false,"attachments":[]}
```

### Где сервис хранит данные

Каталоги задаются в `Settings` и по умолчанию **относительные**: `data/docs`
(документы), `data/index` (индекс), `data/settings.json` (настройки),
`data/logs` (журналы). Относительный путь считается от **рабочего каталога
процесса**, поэтому запускать сервис нужно из корня репозитория — так делает
`make api` (он поднимает uvicorn с `--app-dir backend`, не меняя каталог).
Если запустить из `backend/`, относительные пути уведут в `backend/data/`.

Что сервис реально использует, видно в трёх местах: в журнале при старте
(`рабочий каталог …, документы …, индекс …`), в `GET /api/v1/status`
(`index_dir`) и на странице настроек в блоке «Задано вне интерфейса» — там
показывается уже разрешённый абсолютный путь и рабочий каталог процесса.

Переопределить каталоги можно только окружением: `RAGKB_DOCS_DIR`,
`RAGKB_INDEX_DIR`, `RAGKB_SETTINGS_FILE`, `RAGKB_LOG_DIR` — абсолютными путями
это удобнее всего для systemd и для нестандартных установок.

### Развёртывание на сервере

**Compose (рекомендуемый путь).** Пути уже прописаны в `docker-compose.yml`:
`./data/docs` и `./data/logs` монтируются в контейнер, индекс живёт в томе
`rag_index`, рабочий каталог образа — `/app`. Поэтому относительные значения по
умолчанию подходят для документов, индекса и журналов. Файл настроек требует
отдельного mount, описанного ниже. Пример адресов и подключения к БД:

```bash
POSTGRES_USER=ragkb
POSTGRES_PASSWORD=…           # смените
POSTGRES_DB=ragkb
POSTGRES_HOST=postgres
RAGKB_EMBEDDING_URL=http://host.docker.internal:11434
RAGKB_EMBEDDING_MODEL=qwen3-embedding:0.6b
RAGKB_LLM_URL=http://host.docker.internal:11434/v1
RAGKB_LLM_MODEL=qwen2.5:7b-instruct
```

Модели нужно загрузить на хосте до первого использования. Ollama должна
быть доступна из контейнера по `RAGKB_EMBEDDING_URL` и `RAGKB_LLM_URL`.
Документы загружаются только через `/admin/documents`.

Файл `data/settings.json` в текущем Compose не смонтирован: он переживает
перезапуск, но теряется при пересоздании контейнера. Чтобы сохранять настройки
из интерфейса при обновлениях, создайте каталог `data/config` на хосте
и добавьте `docker-compose.override.yml` рядом с основным Compose:

```yaml
services:
  rag:
    volumes:
      - ./data/config:/app/data/config
    environment:
      RAGKB_SETTINGS_FILE: /app/data/config/settings.json
```

Если настройки уже сохранены, скопируйте существующий JSON из контейнера в
`data/config/settings.json` на хосте до пересоздания контейнера. Настройки
нельзя хранить внутри каталога индекса: при удалении последнего документа
этот каталог удаляется целиком.

**Без контейнеров (venv + systemd).** Базу готовят так же: создать БД,
`RAGKB_DATABASE_URL` задать до `make migrate` и также в окружении юнита. Каталог установки — `/opt/ragkb`, данные
рядом с ним; относительные пути считаются от `WorkingDirectory`:

```ini
[Unit]
Description=ragkb — база знаний
After=network-online.target

[Service]
User=ragkb
WorkingDirectory=/opt/ragkb
EnvironmentFile=/etc/ragkb.env
Environment=RAGKB_DOCS_DIR=/var/lib/ragkb/docs
Environment=RAGKB_INDEX_DIR=/var/lib/ragkb/index
Environment=RAGKB_SETTINGS_FILE=/var/lib/ragkb/settings.json
Environment=RAGKB_LOG_DIR=/var/lib/ragkb/logs
Environment=RAGKB_EMBEDDING_URL=http://127.0.0.1:11434
Environment=RAGKB_LLM_URL=http://127.0.0.1:11434/v1
Environment=RAGKB_LLM_MODEL=qwen2.5:7b-instruct
ExecStart=/opt/ragkb/backend/.venv/bin/uvicorn ragkb.main:app --app-dir /opt/ragkb/backend --host 127.0.0.1 --port 8000
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

Файл `/etc/ragkb.env` должен содержать `RAGKB_DATABASE_URL`; каталоги данных
нужно создать заранее и дать пользователю `ragkb` право записи.

Здесь пути к данным вынесены в `/var/lib/ragkb` и заданы абсолютно: так
обновление кода (замена `/opt/ragkb`) не трогает корпус и индекс. Фронтенд
собирается `bun run build` и запускается `node build` с
`RAGKB_BACKEND_URL=http://127.0.0.1:8000`.

Важно про индекс: в манифесте и в метаданных чанков хранятся пути к исходным
файлам, поэтому смена `RAGKB_DOCS_DIR` (или переезд каталога документов)
требует пересборки индекса. Смена модели эмбеддингов или нарезки тоже требует
пересборки: страница настроек предупреждает об этом сама.

### Настройки

Страница `/admin/settings` правит то, что раньше требовало переменных окружения:
модель и адрес эмбеддингов, параметры поиска (топ-k, веса RRF, MMR, пороги,
реранкер), нарезку чанков, хранилище, генерацию и сведения об организации.

Три слоя значений, от слабого к сильному:

1. умолчания в `backend/ragkb/core/config.py`;
2. окружение `RAGKB_*` (для подключения к БД также корневой `.env`, см. быстрый старт);
3. файл `data/settings.json` — то, что сохранили в интерфейсе.

Файл накладывается поверх окружения при старте, поэтому правка переживает
перезапуск; на странице у каждого поля видно источник («по умолчанию», «из
окружения», «изменено здесь») и есть кнопка «сбросить», возвращающая значение
окружения. Правки применяются сразу, движок при этом сбрасывается, но поиск
успевает заметить расхождение: если настройки разошлись с собранным индексом
(другая модель эмбеддингов, другой размер чанка, другое хранилище), страница
показывает предупреждение и кнопку «Перестроить индекс». Смена `llm.backend` помечена требованием
перезапуска. Настройка логирования применяется при старте процесса: после
смены уровня логов сервис также нужно перезапустить.

Чего на странице нет и почему: каталоги документов и индекса, файл настроек и
строка подключения к БД — они задают, где лежат данные, и меняются только
окружением. Они показаны в блоке «Задано вне интерфейса» (пароль в строке
подключения маскируется).

Авторизации по-прежнему нет: страница настроек открыта всем, у кого есть
доступ к сайту. Ограничения доступа на прокси должны охватывать и страницы `/admin`, и
маршруты управления `/api/admin/*`, `/api/index/rebuild`; прямой доступ
к FastAPI также не должен обходить эти ограничения.

### Документы попадают в базу только через интерфейс

Единственный способ добавить документ — загрузка на `/admin/documents`
(`POST /api/v1/admin/documents`). Реестр `corpus_documents` — источник истины:
индекс собирается по его записям, каталог `data/docs` не обходится вовсе.
Файл, положенный в каталог мимо интерфейса, не индексируется и в списке не
показывается — его можно удалить или загрузить тем же документом через
страницу. Удалять через интерфейс тоже можно только документы корпуса.

Очередь загрузки принимает файлы с `index=false`, затем один раз перестраивает
индекс. Если реестр пуст, пересборка отвечает 400 «В корпусе нет документов:
загрузите их на странице «Документы»».

Без БД (`RAGKB_DATABASE_URL`) реестра нет, а значит нет ни загрузки, ни
индексации: страница документов сообщает, что нужна база. Вопросы могут работать
с уже построенным индексом; при его отсутствии возвращается 503. Это осознанный выбор: документы должны
попадать в базу знаний через интерфейс, а не из каталога файловой системы.

## Скачивание оригиналов

Чат отвечает по фрагментам корпуса и может приложить сам документ. Разрешение
хранится в реестре отдельным полем `download_allowed` и **по умолчанию
выключено** — в том числе у всех документов, загруженных до появления функции.

- **Управление.** Переключатель при загрузке открывает оригинал у новой пачки
  (значение фиксируется для каждого файла очереди: изменение переключателя не
  влияет на уже начатую загрузку), а переключатель в строке таблицы меняет флаг
  у конкретного документа. Как и всё управление документами, это открыто всем
  посетителям: аккаунтов и ролей в сервисе нет.
- **Только выдача.** Флаг не влияет на поиск, ответы и цитаты: закрытый
  документ по-прежнему находится и цитируется, недоступен лишь его файл.
  Разрешение меняется без переиндексации, а вложения кандидатов собираются из
  вопроса и найденных фрагментов, поэтому PDF попадает в набор, даже если ответ
  построен на закрытом DOCX.

### Участие в поиске

Рядом с разрешением на скачивание у каждого документа есть второй
переключатель — «Индексировать». Он решает, попадают ли фрагменты документа в
ответы:

- **выключен** — документ не индексируется: его текст не участвует в поиске, и
  модель по нему не отвечает, поэтому технические требования можно положить в
  корпус, не рискуя выдумыванием по ним;
- **включён** (по умолчанию) — обычное поведение: фрагменты находятся, цитируются
  и попадают в контекст ответа.

Флаги независимы: документ можно исключить из поиска и при этом разрешить
скачивание оригинала — именно так выдаются техтребования (приложить файл можно,
отвечать по нему нельзя). И наоборот: закрытый для скачивания документ остаётся
источником ответов.

Переключатель есть и при загрузке (для новой пачки), и в строке таблицы. В
списке такой документ показан состоянием «исключён из поиска».

**Изменение флага применяется следующей пересборкой индекса**: поиск читает
индекс, а не реестр, поэтому до пересборки документ ещё отвечает. В интерфейсе
после смены флага появляется подсказка и кнопка «Пересобрать индекс».
- **Инструмент.** Оригинал прикладывает инструмент `get_download_link` — нужна
  модель с поддержкой tool calling. Если модель её не поддерживает, вопрос
  завершается явной ошибкой: подмены вызова разбором ссылок в тексте нет.
  Каждый вопрос независим, поэтому при неоднозначном запросе модель просит
  уточнение полной формулировкой, а не угадывает файл.
- **Выдача файла.** `GET` (и `HEAD`) `/api/v1/documents/{document_id}/download`
  отдаёт оригинал только по записи реестра: путь берётся из записи, симлинки и
  выход за каталог запрещены, содержимое открытого файла сверяется с хэшем
  записи. Отзыв разрешения закрывает ссылку сразу, но не отменяет уже начатую
  передачу и не «отзывает» сохранённый файл. Частичных ответов нет: `Range`
  получает полный `200`.
- **Замена и удаление.** При замене файла с тем же именем `document_id`
  сохраняется, а разрешение не наследуется: оно берётся из явного значения
  загрузки. После удаления документа старая ссылка перестаёт работать.

### Ограничение частоты скачиваний

Ограничения стоят на BFF (порт frontend), потому что именно он публикуется
наружу: в Compose backend доступен только изнутри сети. Значения задаются
окружением:

```
RAGKB_DOWNLOAD_RATE_PER_MINUTE=10   # запросов в минуту на адрес клиента
RAGKB_DOWNLOAD_BURST=3              # короткий всплеск
RAGKB_DOWNLOAD_MAX_CONCURRENT=2     # одновременных передач на адрес
RAGKB_DOWNLOAD_MAX_KEYS=10000       # сколько адресов помнится
```

Отказ приходит как `429` с `Retry-After`, и до backend запрос не доходит.
Адрес берётся из соединения (`getClientAddress()`), заголовки браузера не
читаются. `ADDRESS_HEADER` и `XFF_DEPTH` включают только вместе с закрытым
прямым доступом к BFF и доверенным прокси, который перезаписывает заголовок;
иначе посетитель подставит себе любой адрес и обойдёт ограничение. Счётчики
живут в памяти одного процесса frontend: при нескольких репликах нужен общий
ограничитель или ограничение на внешнем прокси. Частота и параллелизм не
задают потолок трафика — для бюджета байтов нужна отдельная квота.

### Журнал

Изменение разрешения пишется строкой `event=download_permission` с прежним и
новым значением, идентификатором документа и меткой запроса (`X-Request-Id`,
её создаёт BFF). События передачи — начало, завершение, обрыв — и адрес клиента
пишет BFF; метка связывает строки frontend и backend. Адрес означает источник
запроса, а не личность: учётных записей в сервисе нет, и за общим NAT у
нескольких посетителей он один. Содержимое документов в журнал не попадает.

## Оценка качества

RAG почти всегда ломается в поиске, а не в генерации: если нужного фрагмента нет
в top-k, никакая модель не поможет. Поэтому мерить надо в первую очередь поиск —
и на своих документах, а не на публичных бенчмарках.

```bash
uv run --project backend python backend/examples/eval.py backend/examples/eval_set.jsonl -k 5
```

Скрипт читает `Settings()` без переопределений из `data/settings.json`:
Перед запуском согласуйте конфигурацию скрипта с собранным индексом:
адреса, модель и пути задаются окружением; параметры без переменных окружения
нужно передать через `Settings` в отдельном сценарии оценки.
`ablation.py` читает набор по пути `examples/eval_set.jsonl` относительно
рабочего каталога, поэтому его запускают из `backend/`, явно указывая
абсолютные `RAGKB_INDEX_DIR` и `RAGKB_DOCS_DIR` вашего корпуса:

```bash
RAGKB_INDEX_DIR="$PWD/data/index" RAGKB_DOCS_DIR="$PWD/data/docs" \
  sh -c 'cd backend && uv run python examples/ablation.py'
```

Исторический замер при переходе на LangChain (21 сентября 2026 года) на реальном документе (FAQ, 146 чанков, эмбеддинги `qwen3-embedding:0.6b`
в Ollama, 27 вопросов, собранных из заголовков и числовых фраз документа):

```
режим                Hit@1   Hit@3   Hit@5     MRR
только BM25          48.1%   81.5%   88.9%   0.659
только векторы       51.9%   63.0%   70.4%   0.586
гибрид (RRF)         59.3%   77.8%   88.9%   0.703
гибрид + MMR         59.3%   77.8%   81.5%   0.688
```

Гибрид выигрывает по MRR, MMR на этом корпусе слегка снижает Hit@5 — если у вас
так же, выключите его (`retrieval.use_mmr: false`). Набор небольшой и собран
автоматически, поэтому цифры читайте как ориентир: на своих вопросах из реальных
обращений картина может отличаться, и прогонять `ablation.py` нужно на них.

Формат тестового набора — JSONL:

```json
{"question": "За сколько дней подавать заявление на отпуск?", "expected": ["не позднее чем за 14 календарных дней"], "doc": "reglament_otpuska"}
```

50–100 таких вопросов, собранных из реальных обращений, дадут больше пользы, чем
любые эвристики по подбору размера чанка.

## Настройка

Настройки описаны в `backend/ragkb/core/config.py`; переменные окружения
(`RAGKB_LLM_BACKEND`, `RAGKB_EMBEDDING_MODEL` и т.д.) перекрывают значения по умолчанию,
а сохранённые настройки интерфейса перекрывают окружение.

Что обычно приходится крутить:

- `chunking.size` — 900 символов подходит для регламентов. Для плотных технических
  текстов имеет смысл 500–600, для повествовательных — 1200–1500.
- `embedding.backend`, `embedding.base_url`, `embedding.model` — чем считать
  векторы и где живёт этот сервис: `ollama` (корень без `/v1`) или `openai`
  (OpenAI-совместимый корень с `/v1`). В окружении — `RAGKB_EMBEDDING_BACKEND`,
  `RAGKB_EMBEDDING_URL`, `RAGKB_EMBEDDING_MODEL`, ключ — `RAGKB_EMBEDDING_API_KEY`.
- `embedding.timeout` — 300 с: первый запрос поднимает модель в память.
  `embedding.keep_alive` — сколько держать её загруженной после индексации
  (`30m`; значение переводится в секунды для клиента Ollama).
- `retrieval.candidates` — сколько кандидатов берёт каждая половина поиска до
  слияния. Больше = выше recall, дороже MMR и реранк.
- `retrieval.min_score` — порог, ниже которого система отвечает «не найдено».
  Ставится по измерению на своём наборе; по умолчанию выключен (0.0).
- `store.hnsw_search_ef` — полнота приближённого поиска. Больше = выше recall и
  медленнее запрос. Трогать имеет смысл, только если `examples/eval.py` показал потери.

Смена `store.backend`, модели эмбеддингов или её размерности требует полной
переиндексации — система проверяет это по манифесту и отказывается работать на
рассогласованном индексе, а не выдаёт молча мусор.

## Ограничения

- **Эмбеддинги считает внешний сервис.** Либо Ollama (по умолчанию), либо
  OpenAI-совместимый HTTP-сервер (`embedding.backend: openai`): без него (или
  без загруженной модели) индекс не собрать. Бэкенд `fake`
  (`DeterministicFakeEmbedding`) нужен только тестам: он даёт детерминированные
  векторы без сети.
- **Сканы без текстового слоя** не читаются — нужен OCR (`pytesseract` + `pdf2image`),
  подключается в `loaders._pdf_pages`.
- **Стеммер — правила, а не морфология.** Ошибается на нерегулярных формах.
  `pymorphy3` точнее, если готовы на зависимость.
- **Инкрементального обновления индекса нет.** Любая правка корпуса —
  пересборка целиком через интерфейс; точечно удаляется только документ
  (`DELETE /api/v1/admin/documents/{name}`).
- **BM25 строится в памяти процесса** при открытии движка, то есть после каждой
  пересборки индекса. На миллионах чанков это заметно; тогда лексический поиск
  стоит вынести в OpenSearch.
- **Смена участия в поиске требует пересборки.** Пока индекс не пересобран,
  исключённый документ продолжает отвечать, а включённый — ещё не ищется:
  интерфейс говорит об этом прямо и предлагает пересобрать индекс.
- **Разрешение на скачивание открыто всем.** Отдельных ролей и подтверждений
  нет: любой посетитель может открыть или закрыть оригинал, как и загрузить
  документ. Это настройка публикации, а не право доступа.
- **Скачанный файл нельзя отозвать.** Закрытие флага блокирует будущие
  запросы, но уже сохранённую копию не возвращает; аудит не устанавливает
  личность скачавшего.
- **Нужна модель с tool calling.** Без поддержки инструментов вопрос
  завершается ошибкой, а не ответом без вложений.
- **Ядро завязано на LangChain 1.x.** Мажорное обновление фреймворка — это
  правка `core/documents.py`, `core/vectorstore.py`, `core/retrieval.py` и
  `core/pipeline.py`; слои `api/` и `services/` от версии не зависят, и это
  проверяется архитектурным тестом.

## Структура

```
backend/ragkb/
  api/         FastAPI: routes, schemas, deps, обработка ошибок
  core/        LangChain-ядро: documents, vectorstore, retrieval, pipeline,
               конфиг, движок БД, доменные ошибки
  db/          реестр документов (SQLAlchemy: Postgres или SQLite)
  domain/      сущности и порты
  services/    сценарии приложения (без FastAPI, SQLAlchemy и LangChain):
               документы, выдача оригиналов, кандидаты на скачивание, ответ
  main.py      app — вход uvicorn и композиционный корень
frontend/       SvelteKit, BFF: проксирование, ограничение и журнал скачиваний
```
