# ragkb — RAG-система над базой знаний

Вопрос-ответ по корпоративным документам (PDF, DOCX, MD, TXT, HTML) с обязательными
ссылками на источники. Всё работает on-premise: документы, индекс и модели не покидают
ваш контур.

## Что внутри

```
документы → парсинг → чанкинг → эмбеддинги ─┐
                          └──→ BM25 ─────────┤
                                             ├→ RRF → MMR/реранк → промпт → LLM → ответ + ссылки
                          запрос ────────────┘
```

Ключевые решения и почему они такие:

| Решение | Причина |
|---|---|
| **Гибридный поиск** (BM25 + векторы) | Векторы ловят перефразировки, BM25 — точные сущности: номера приказов, артикулы, аббревиатуры. По отдельности каждый заметно проваливается. |
| **Слияние через RRF**, а не сумму оценок | BM25 выдаёт 0…30, косинус 0…1 — складывать их нельзя. RRF работает с рангами и не требует калибровки. |
| **Чанк несёт путь заголовков** | Запрос «срок оплаты отпуска» найдёт абзац, где слово «отпуск» есть только в заголовке раздела. |
| **Стемминг для русского** | «отпуска», «отпуску», «отпуском» — для BM25 это три разных токена без нормализации. |
| **MMR в выдаче** | Иначе top-5 часто оказывается пятью вариациями одного абзаца, и модель не видит альтернатив. |
| **Обязательные ссылки [N]** | Проверяемость ответа сама по себе снижает выдумывание и позволяет пользователю дойти до первоисточника. |
| **ChromaDB как хранилище** | HNSW-индекс, персистентность из коробки, фильтры по метаданным и — главное — точечное добавление/удаление документов без переиндексации корпуса. |

## Векторное хранилище

Основной бэкенд — **ChromaDB** во встроенном режиме: отдельный сервис поднимать
не нужно, база лежит файлами в `data/index/chroma`. При необходимости
переключается на отдельный сервер Chroma одной строкой (`store.chroma_host`).

Два решения, которые стоит знать:

- **Векторы считаем сами.** Коллекция создаётся с `embedding_function=None`, и в
  Chroma передаются готовые векторы нашего эмбеддера. Иначе Chroma подставит свою
  модель по умолчанию, и индекс молча разойдётся с запросами.
- **Метрика — cosine, а не L2 по умолчанию.** Векторы нормализованы, косинус
  согласуется с порогом `retrieval.min_score`. Chroma возвращает *дистанцию*
  (`1 - cos`), мы приводим её обратно к близости — есть тест, который ловит
  случайный переворот шкалы.

BM25 остаётся нашим: `where_document` в Chroma — это фильтр по вхождению
подстроки, а не ранжирование, для гибридной схемы он не годится. Инвертированный
индекс лежит рядом с базой и пересобирается при каждом изменении корпуса.

Второй бэкенд — `numpy`: матрица в памяти и точный перебор, без chromadb вообще.
Полезен в тестах и на маленьких корпусах, где хочется гарантированно точного
поиска. Переключается в `config.yaml` → `store.backend`.

Замер на этой машине (CPU, 20 000 векторов × 384, top-10, кластеризованные
данные — настоящие эмбеддинги тоже группируются по темам):

```
numpy, точный перебор     0.9 мс/запрос,  recall@10 100%
chroma, HNSW ef=100       2.0 мс/запрос,  recall@10 100%
chroma, HNSW ef=400       2.9 мс/запрос,  recall@10 100%
```

На таком объёме перебор быстрее — HNSW начинает выигрывать после сотен тысяч
векторов, а до этого платит за обход графа. Берём Chroma не ради скорости поиска,
а ради инкрементальных обновлений и того, что не нужно держать всю матрицу в
памяти процесса. Проверить на своём объёме: `python backend/examples/bench_store.py 200000 1024`.

Отдельно про recall: HNSW — приближённый поиск. На кластеризованных данных он
находит всё, но на близком к равномерному шуму распределении recall@10 падает
примерно до 60% при тех же настройках. Если ваши документы очень разнородны,
поднимите `store.hnsw_search_ef` и померьте `python backend/examples/eval.py` до и после.

## Быстрый старт

Авторизации, аккаунтов и истории нет. Сайт сразу открывает чат; документы и
управление индексом доступны всем посетителям. Переписка живёт только в памяти
страницы и исчезает после обновления. Каждый вопрос обрабатывается независимо.

Из корня репозитория:

```bash
make sync
make sync-frontend
make migrate
make api
```

В другом терминале: `make frontend`, затем открыть `http://localhost:5173`.
Загрузить или принять документы на `/admin/documents`, перестроить индекс.
Без URL БД реестр отключён: индексируется весь каталог документов, о чём

По умолчанию доступны TF-IDF и экстрактивный ответ без внешних моделей.
Настройки задаются в `Settings` и переменных окружения `RAGKB_*`; для вложенных
параметров RAGKB_* должны быть в окружении процесса (Compose делает это через env_file).

## Боевая конфигурация

Compose запускает Postgres, миграции, backend и frontend. Сервис создания
администратора отсутствует. Postgres используется для реестра документов.

```bash
cp .env.example .env
# Задайте параметры БД и адрес OpenAI-совместимого LLM в .env.
docker compose up -d --build
```

Интерфейс доступен на порту 3000. Внешний Angie при использовании должен
проксировать сайт на frontend без прежних правил входа и OIDC.

Генерация — OpenAI-совместимый HTTP (`RAGKB_LLM_URL`, обычно корень `…/v1`).
Эмбеддинги в контейнере rag — sentence-transformers, BAAI/bge-m3; веса
сохраняются в томе rag_hf. Ollama и LLM-сервера в Compose нет.
Каталог `./data/docs` смонтирован на запись для загрузки документов через UI.
Смена эмбеддера требует перестроения индекса.

Существующие таблицы аккаунтов, сессий, диалогов и оценок после обновления
не читаются и не заполняются. Старые данные автоматически не удаляются;
цепочка миграций сохранена для обновления существующих установок.

### Что выбрать

**Эмбеддинги.** `bge-m3` — мультиязычная, 8k контекста, хорошо держит русский.
`intfloat/multilingual-e5-large` — сопоставима, но требует префиксов
`query: ` / `passage: ` (задаются в `embedding.query_prefix` / `doc_prefix`).
`nomic-embed-text` — легче и быстрее, на русском слабее.

**LLM.** `qwen2.5:14b-instruct` — разумный минимум для русского RAG на одной
видеокарте 12–16 ГБ. Для 24 ГБ+ имеет смысл `qwen2.5:14b/32b`. Температура 0.1:
задача — пересказать контекст, а не сочинять.

**Реранкер.** `retrieval.reranker: sentence-transformers` с `bge-reranker-v2-m3`
обычно даёт +5–15 п.п. к точности top-5, ценой ~100–300 мс на запрос. Включать
стоит после того, как измерите базовое качество.

## Команды

Консольной точки входа больше нет. Сервер — uvicorn, индекс — `POST /api/v1/index/rebuild`,
оценка поиска — `python backend/examples/eval.py`.

## HTTP API

Браузер ходит только через BFF SvelteKit: `/api/ask` → `/api/v1/ask`.
Все маршруты открыты, cookie и заголовки идентификации не используются.

| Метод | Назначение |
|---|---|
| `GET /health` | Живость и наличие индекса |
| `GET /api/v1/status` | Сведения об индексе и моделях |
| `GET /api/v1/bootstrap?session_id=` | Версия, организация, модели и индекс; UUID вкладки для телеметрии |
| `GET /api/v1/models` | Каталог моделей |
| `GET /api/v1/organization` | Сведения об организации, 404 если не настроена |
| `POST /api/v1/search` | Поиск без генерации |
| `POST /api/v1/ask` | Независимый вопрос, ответ потоком NDJSON |
| `POST /api/v1/events` | Телеметрия, до 100 событий |
| `POST /api/v1/index/rebuild` | Перестроение индекса |
| `GET /api/v1/admin/documents` | Файлы и состояние индексации |
| `POST /api/v1/admin/documents` | Multipart-загрузка; `?index=false` откладывает индексацию |
| `POST /api/v1/admin/documents/accept` | Принятие файлов из каталога в корпус |
| `DELETE /api/v1/admin/documents/{name}` | Удаление файла и записи индекса |

Тело вопроса: `question`, необязательные `model`, `top_k` (1–20), `expand`.
Модель проверяется по каталогу. История, идентификатор диалога и пользователя
не принимаются. Ответ завершается событием done с источниками; при обрыве
после первого токена `truncated` истинно. При недоступной генерации до первого
токена используется экстрактивный ответ.

```json
{"type":"token","text":"Ежегодный "}
{"type":"done","sources":[],"warnings":[],"elapsed_sec":0.2,"model":"extractive","truncated":false}
```

### Документы попадают в базу через интерфейс

При подключённой БД реестр `corpus_documents` — источник истины. Файл,
положенный в `data/docs` вручную, отображается как «вне корпуса», пока его
не примут на `/admin/documents`. Записываются дата и способ принятия;
личность загрузившего больше не фиксируется.

Очередь загрузки принимает файлы с `index=false`, затем один раз перестраивает
индекс. Если реестр пуст, сначала примите документы. Без подключения БД
индексируется весь каталог; интерфейс явно предупреждает об этом.

## Оценка качества

RAG почти всегда ломается в поиске, а не в генерации: если нужного фрагмента нет
в top-k, никакая модель не поможет. Поэтому мерить надо в первую очередь поиск —
и на своих документах, а не на публичных бенчмарках.

```bash
cd backend
python examples/eval.py examples/eval_set.jsonl -k 5
python examples/ablation.py
python examples/bench_store.py
```

На демо-корпусе (5 документов, 23 чанка, 15 вопросов, TF-IDF без нейросетей):

```
режим                Hit@1   Hit@3   Hit@5     MRR
только BM25          93.3%   93.3%  100.0%   0.950
только векторы       93.3%   93.3%  100.0%   0.950
гибрид (RRF)         93.3%   93.3%  100.0%   0.950
гибрид + MMR         93.3%  100.0%  100.0%   0.967
```

Оговорка: корпус маленький, а TF-IDF по природе близок к BM25, поэтому «векторная»
строка здесь не показывает реальной пользы плотного поиска. Разница между режимами
проявляется на настоящих эмбеддингах и корпусе от нескольких сотен документов —
прогоните `ablation.py` на своих данных перед выбором конфигурации.

Формат тестового набора — JSONL:

```json
{"question": "За сколько дней подавать заявление на отпуск?", "expected": ["не позднее чем за 14 календарных дней"], "doc": "reglament_otpuska"}
```

50–100 таких вопросов, собранных из реальных обращений, дадут больше пользы, чем
любые эвристики по подбору размера чанка.

## Настройка

Настройки описаны в `backend/ragkb/core/config.py`; переменные окружения
(`RAGKB_LLM_BACKEND`, `RAGKB_EMBEDDING_MODEL` и т.д.) перекрывают значения по умолчанию.

Что обычно приходится крутить:

- `chunking.size` — 900 символов подходит для регламентов. Для плотных технических
  текстов имеет смысл 500–600, для повествовательных — 1200–1500.
- `retrieval.candidates` — сколько кандидатов идёт в реранк. Больше = выше recall,
  дороже реранк.
- `retrieval.min_score` — порог, ниже которого система отвечает «не найдено».
  Ставится по измерению на своём наборе; по умолчанию выключен (0.0).
- `store.hnsw_search_ef` — полнота приближённого поиска. Больше = выше recall и
  медленнее запрос. Трогать имеет смысл, только если `examples/eval.py` показал потери.

Смена `store.backend` или модели эмбеддингов требует полной переиндексации —
система проверяет это по манифесту и отказывается работать на рассогласованном
индексе, а не выдаёт молча мусор.

## Ограничения

- **Сканы без текстового слоя** не читаются — нужен OCR (`pytesseract` + `pdf2image`),
  подключается в `loaders._pdf_pages`.
- **Стеммер — правила, а не морфология.** Ошибается на нерегулярных формах.
  `pymorphy3` точнее, если готовы на зависимость.
- **Инкрементальное обновление индекса снаружи недоступно** (CLI `update`/`delete`
  сняты). Код в `core/pipeline.py` остался. С TF-IDF словарь IDF заморожен на
  полной индексации — новые термины хуже находятся плотным поиском.
- **BM25 пересобирается целиком** при каждом изменении корпуса в коде
  `update`/`delete`. На миллионах чанков это заметно; тогда лексический поиск
  стоит вынести в OpenSearch.

```
backend/ragkb/
  api/         FastAPI: routes, schemas, deps, обработка ошибок
  core/        поиск и генерация, конфиг, движок БД, доменные ошибки

```
