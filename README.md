# ragkb — RAG-система над базой знаний

Вопрос-ответ по корпоративным документам (PDF, DOCX, MD, TXT, HTML) с обязательными
ссылками на источники. Всё работает on-premise: документы, индекс и модели не покидают
ваш контур.

## Что внутри

```
документы → парсинг → секции → чанки → эмбеддинги ─┐
                                       └──→ BM25 ──┤
                                                   ├→ RRF → MMR/реранк → промпт → LLM → ответ + ссылки
                                    запрос ────────┘
```

Ядро собрано на **LangChain**: цепочка ответа — LCEL (`prompt | ChatOpenAI |
StrOutputParser`), ретриверы, сплиттер и хранилище — его же объекты. Наружу это
не выходит: `core/ports.py` описывает `AnswerEngine`, а прикладной слой
(`api/`, `services/`) LangChain не импортирует — правило закреплено тестом
`tests/test_architecture.py`.

Ключевые решения и почему они такие:

| Решение | Причина |
|---|---|
| **Гибридный поиск** (BM25 + векторы) | Векторы ловят перефразировки, BM25 — точные сущности: номера приказов, артикулы, аббревиатуры. По отдельности каждый заметно проваливается. |
| **Слияние через RRF**, а не сумму оценок | BM25 выдаёт 0…30, косинус 0…1 — складывать их нельзя. RRF работает с рангами и не требует калибровки. |
| **Чанк несёт путь заголовков** | Запрос «срок оплаты отпуска» найдёт абзац, где слово «отпуск» есть только в заголовке раздела. |
| **Стемминг для русского** | «отпуска», «отпуску», «отпуском» — для BM25 это три разных токена без нормализации. |
| **MMR в выдаче** | Иначе top-5 часто оказывается пятью вариациями одного абзаца, и модель не видит альтернатив. |
| **Обязательные ссылки [N]** | Проверяемость ответа сама по себе снижает выдумывание и позволяет пользователю дойти до первоисточника. |
| **ChromaDB как хранилище** | HNSW-индекс, персистентность из коробки, фильтры по метаданным; в LangChain это `langchain-chroma`, поэтому точечное удаление документа осталось. |
| **Генерация обязательна** | Экстрактивного ответа «из найденных фрагментов» больше нет: если модель недоступна, вопрос отклоняется с 503 до открытия потока, а не подменяется пересказом. |

## Хранилище

Основной бэкенд — **ChromaDB** во встроенном режиме через `langchain-chroma`:
отдельный сервис поднимать не нужно, база лежит файлами в `data/index/chroma`.
При необходимости переключается на отдельный сервер Chroma (`store.chroma_host`).
Второй бэкенд — `memory` (`InMemoryVectorStore` из langchain-core): он нужен
тестам, чтобы не зависеть от chromadb и диска.

Два решения, которые стоит знать:

- **Метрика — cosine, а не L2 по умолчанию.** Коллекция создаётся с
  `hnsw:space: cosine`, и близость согласуется с порогом `retrieval.min_score`.
- **Векторы считает эмбеддер LangChain** (`langchain-ollama`), а хранилище
  только складывает готовые — своей embedding-функции у коллекции нет.

BM25 остаётся нашим: `langchain_classic.retrievers.BM25Retriever` — это шим на
устаревший `langchain-community`, поэтому лексическая половина реализована как
`LexicalRetriever(BaseRetriever)` на `rank-bm25` с русской токенизацией.
Слияние с плотным поиском делает `EnsembleRetriever` (RRF), а не свой код.

Отдельно про recall: HNSW — приближённый поиск. На кластеризованных данных он
находит всё, но на близком к равномерному шуму распределении recall падает
примерно до 60% при тех же настройках. Если ваши документы очень разнородны,
поднимите `store.hnsw_search_ef` и померьте `backend/examples/eval.py` до и после.

## Быстрый старт

Авторизации, аккаунтов и истории нет. Сайт сразу открывает чат; документы и
управление индексом доступны всем посетителям. Переписка живёт только в памяти
страницы и исчезает после обновления. Каждый вопрос обрабатывается независимо.

Из корня репозитория:

```bash
make sync
make sync-frontend
make migrate
make api
```

В другом терминале: `make frontend`, затем открыть `http://localhost:5173`.
Загрузить или принять документы на `/admin/documents`, перестроить индекс.
Без URL БД реестр отключён: индексируется весь каталог документов, о чём
интерфейс предупреждает.

Эмбеддинги считает Ollama — её нужно поставить и загрузить модель:

```bash
ollama pull qwen3-embedding:0.6b
```

Адрес по умолчанию — `http://127.0.0.1:11434`, модель —
`qwen3-embedding:0.6b` (обе настройки перекрываются `RAGKB_EMBEDDING_URL` и
`RAGKB_EMBEDDING_MODEL`). Если Ollama не отвечает или модель не загружена,
перестроение индекса возвращает 503 с готовой подсказкой — молча собрать
индекс «на других векторах» нельзя.

Генерация больше не опциональна: экстрактивного ответа нет, поэтому нужен
OpenAI-совместимый сервер — `RAGKB_LLM_URL` (обычно корень с `/v1`) и
`RAGKB_LLM_MODEL`. Подойдёт сама Ollama: `RAGKB_LLM_URL=http://127.0.0.1:11434/v1`.
Без адреса `POST /api/v1/ask` отвечает 503 «Генерация недоступна».

Настройки задаются в `Settings` (`backend/ragkb/core/config.py`) и переменных
окружения `RAGKB_*`; для вложенных параметров RAGKB_* должны быть в окружении
процесса (Compose делает это через env_file).

## Боевая конфигурация

Compose запускает Postgres, миграции, backend и frontend. Сервис создания
администратора отсутствует. Postgres используется для реестра документов.

```bash
cp .env.example .env
# Задайте параметры БД, адрес Ollama и адрес OpenAI-совместимого LLM в .env.
ollama pull qwen3-embedding:0.6b
docker compose up -d --build
```

Интерфейс доступен на порту 3000. Внешний Angie при использовании должен
проксировать сайт на frontend без прежних правил входа и OIDC.

Эмбеддинги считает Ollama на хост-машине: контейнер `rag` обращается к ней по
`host.docker.internal:11434` (адрес задан в `Dockerfile` и перекрывается
`RAGKB_EMBEDDING_URL`). Сервиса Ollama в Compose нет — модели остаются под
управлением `ollama pull`, а образ `rag` не тащит torch и веса эмбеддера.
Генерация — OpenAI-совместимый HTTP (`RAGKB_LLM_URL`, обычно корень `…/v1`);
на неё можно указать и саму Ollama.
Каталог `./data/docs` смонтирован на запись для загрузки документов через UI.
Смена модели эмбеддингов (как и её размерности) требует перестроения индекса:
движок отказывается искать векторами другой модели, а не выдаёт молча мусор.

Существующие таблицы аккаунтов, сессий, диалогов и оценок после обновления
не читаются и не заполняются. Старые данные автоматически не удаляются;
цепочка миграций сохранена для обновления существующих установок.

### Что выбрать

**Эмбеддинги (Ollama).** `qwen3-embedding:0.6b` — значение по умолчанию: 1024
координаты, 32k контекста, 639 МБ, хорошо держит русский. `bge-m3` — та же
размерность и качество на русском, но 1.2 ГБ; брать, если уже загружена.
`nomic-embed-text` (768) легче и быстрее, на русском слабее, а его контекст
2048 токенов при чанке 900 символов близок к пределу. `embeddinggemma` (768) —
компромисс для многоязычных корпусов. Модели с обязательными префиксами
(`multilingual-e5`) требуют `embedding.query_prefix` / `doc_prefix`.
Размерность модели попадает в манифест индекса: смена модели на модель другой
размерности — это всегда полная переиндексация.

**LLM.** `qwen2.5:14b-instruct` — разумный минимум для русского RAG на одной
видеокарте 12–16 ГБ. Для 24 ГБ+ имеет смысл `qwen2.5:14b/32b`. Температура 0.1:
задача — пересказать контекст, а не сочинять. Генерация ходит по
OpenAI-совместимому HTTP, поэтому подойдёт и Ollama — укажите её корень с `/v1`.

**Реранкер.** Только внешний по HTTP: `retrieval.reranker: http` и
`retrieval.reranker_url` (Jina/Cohere-совместимый `/rerank`). Обычно даёт
+5–15 п.п. к точности top-5 ценой ~100–300 мс на запрос. Локальный
cross-encoder не поддерживается: он требует torch, которого в образе нет.
Включать стоит после того, как измерите базовое качество.

## Команды

Консольной точки входа больше нет. Сервер — uvicorn, индекс — `POST /api/v1/index/rebuild`,
оценка поиска — `python backend/examples/eval.py`.

## HTTP API

Браузер ходит только через BFF SvelteKit: `/api/ask` → `/api/v1/ask`.
Все маршруты открыты, cookie и заголовки идентификации не используются.

| Метод | Назначение |
|---|---|
| `GET /health` | Живость и наличие индекса |
| `GET /api/v1/status` | Сведения об индексе и моделях |
| `GET /api/v1/bootstrap?session_id=` | Версия, организация, модели и индекс; UUID вкладки для телеметрии |
| `GET /api/v1/models` | Каталог моделей |
| `GET /api/v1/organization` | Сведения об организации, 404 если не настроена |
| `POST /api/v1/search` | Поиск без генерации |
| `POST /api/v1/ask` | Независимый вопрос, ответ потоком NDJSON |
| `POST /api/v1/events` | Телеметрия, до 100 событий |
| `POST /api/v1/index/rebuild` | Перестроение индекса |
| `GET /api/v1/admin/documents` | Файлы и состояние индексации |
| `POST /api/v1/admin/documents` | Multipart-загрузка; `?index=false` откладывает индексацию |
| `POST /api/v1/admin/documents/accept` | Принятие файлов из каталога в корпус |
| `DELETE /api/v1/admin/documents/{name}` | Удаление файла и записи индекса |

Тело вопроса: `question`, необязательные `model`, `top_k` (1–20), `expand`.
Модель проверяется по каталогу. История, идентификатор диалога и пользователя
не принимаются. Ответ завершается событием done с источниками; при обрыве
после первого токена `truncated` истинно. Если генерация не настроена, запрос
отклоняется с 503 до открытия потока; если модель отказала посреди ответа,
поток завершается с `truncated` и предупреждением.

```json
{"type":"token","text":"Ежегодный "}
{"type":"done","sources":[],"warnings":[],"elapsed_sec":0.2,"model":"qwen2.5:7b-instruct","truncated":false}
```

### Документы попадают в базу через интерфейс

При подключённой БД реестр `corpus_documents` — источник истины. Файл,
положенный в `data/docs` вручную, отображается как «вне корпуса», пока его
не примут на `/admin/documents`. Записываются дата и способ принятия;
личность загрузившего больше не фиксируется.

Очередь загрузки принимает файлы с `index=false`, затем один раз перестраивает
индекс. Если реестр пуст, сначала примите документы. Без подключения БД
индексируется весь каталог; интерфейс явно предупреждает об этом.

## Оценка качества

RAG почти всегда ломается в поиске, а не в генерации: если нужного фрагмента нет
в top-k, никакая модель не поможет. Поэтому мерить надо в первую очередь поиск —
и на своих документах, а не на публичных бенчмарках.

```bash
cd backend
python examples/eval.py examples/eval_set.jsonl -k 5
python examples/ablation.py
```

Замер на реальном документе (FAQ, 146 чанков, эмбеддинги `qwen3-embedding:0.6b`
в Ollama, 27 вопросов, собранных из заголовков и числовых фраз документа):

```
режим                Hit@1   Hit@3   Hit@5     MRR
только BM25          48.1%   81.5%   88.9%   0.659
только векторы       51.9%   63.0%   70.4%   0.586
гибрид (RRF)         59.3%   77.8%   88.9%   0.703
гибрид + MMR         59.3%   77.8%   81.5%   0.688
```

Гибрид выигрывает по MRR, MMR на этом корпусе слегка снижает Hit@5 — если у вас
так же, выключите его (`retrieval.use_mmr: false`). Набор небольшой и собран
автоматически, поэтому цифры читайте как ориентир: на своих вопросах из реальных
обращений картина может отличаться, и прогонять `ablation.py` нужно на них.

Формат тестового набора — JSONL:

```json
{"question": "За сколько дней подавать заявление на отпуск?", "expected": ["не позднее чем за 14 календарных дней"], "doc": "reglament_otpuska"}
```

50–100 таких вопросов, собранных из реальных обращений, дадут больше пользы, чем
любые эвристики по подбору размера чанка.

## Настройка

Настройки описаны в `backend/ragkb/core/config.py`; переменные окружения
(`RAGKB_LLM_BACKEND`, `RAGKB_EMBEDDING_MODEL` и т.д.) перекрывают значения по умолчанию.

Что обычно приходится крутить:

- `chunking.size` — 900 символов подходит для регламентов. Для плотных технических
  текстов имеет смысл 500–600, для повествовательных — 1200–1500.
- `embedding.base_url`, `embedding.model` — адрес Ollama и модель эмбеддингов
  (в окружении `RAGKB_EMBEDDING_URL`, `RAGKB_EMBEDDING_MODEL`).
- `embedding.timeout` — 300 с: первый запрос поднимает модель в память.
  `embedding.keep_alive` — сколько держать её загруженной после индексации
  (`30m`; значение переводится в секунды для клиента Ollama).
- `retrieval.candidates` — сколько кандидатов берёт каждая половина поиска до
  слияния. Больше = выше recall, дороже MMR и реранк.
- `retrieval.min_score` — порог, ниже которого система отвечает «не найдено».
  Ставится по измерению на своём наборе; по умолчанию выключен (0.0).
- `store.hnsw_search_ef` — полнота приближённого поиска. Больше = выше recall и
  медленнее запрос. Трогать имеет смысл, только если `examples/eval.py` показал потери.

Смена `store.backend`, модели эмбеддингов или её размерности требует полной
переиндексации — система проверяет это по манифесту и отказывается работать на
рассогласованном индексе, а не выдаёт молча мусор.

## Ограничения

- **Эмбеддинги считает Ollama.** Без неё (или без загруженной модели) индекс не
  собрать. Бэкенд `fake` (`DeterministicFakeEmbedding`) нужен только тестам:
  он даёт детерминированные векторы без сети.
- **Сканы без текстового слоя** не читаются — нужен OCR (`pytesseract` + `pdf2image`),
  подключается в `loaders._pdf_pages`.
- **Стеммер — правила, а не морфология.** Ошибается на нерегулярных формах.
  `pymorphy3` точнее, если готовы на зависимость.
- **Инкрементального обновления индекса нет.** Любая правка корпуса —
  пересборка целиком через интерфейс; точечно удаляется только документ
  (`DELETE /api/v1/admin/documents/{name}`).
- **BM25 строится в памяти процесса** при открытии движка, то есть после каждой
  пересборки индекса. На миллионах чанков это заметно; тогда лексический поиск
  стоит вынести в OpenSearch.
- **Ядро завязано на LangChain 1.x.** Мажорное обновление фреймворка — это
  правка `core/documents.py`, `core/vectorstore.py`, `core/retrieval.py` и
  `core/pipeline.py`; слои `api/` и `services/` от версии не зависят, и это
  проверяется архитектурным тестом.
## Структура

```
backend/ragkb/
  api/         FastAPI: routes, schemas, deps, обработка ошибок
  core/        LangChain-ядро: documents, vectorstore, retrieval, pipeline,
               конфиг, движок БД, доменные ошибки
  db/          реестр документов (SQLAlchemy: Postgres или SQLite)
  domain/      сущности и порты
  services/    сценарии приложения (без FastAPI, SQLAlchemy и LangChain)
  main.py      app — вход uvicorn и композиционный корень
frontend/       SvelteKit, BFF
```
